## Genuine missing seam implemented

Accepted `20261115023736` customer getters deliberately compare `auth.uid()` to the consenting customer. A staff issuer cannot safely call them or change JWT/GUC identity to impersonate the customer. The new ungranted private function `lock_linked_offline_reward_issuer_consent(preparation UUID, consent_request UUID)` keeps the actual current owner/operator identity, derives the actual customer/link from immutable original consent/proposal, and proves current independent consent against the exact locked hold. No caller-supplied profile/customer/phone/email/approval flag/token is accepted.

It validates the actual owner session and original operator/preparation/proposal association; current actual confirmed customer Auth row and unchanged email confirmation/hash; the independently consenting session still exists and is unexpired; actual customer row with no active staff role; current unrevoked canonical link plus exact original receipt claim and owner decision; unchanged full contact set; no financial withdrawal; no preparation close; actual exact unexpired quote/hold, claims, original allocation terms, benefit availability/price and direct financial refund/reversal facts. It recomputes the proposal fingerprint and fixed proposal-specific AR/EN notice against the saved customer's exact assent. No history/wallet read-consent or gate is used.

Return state `locked_consent_valid` contains private source witness and IDs, actual operator/customer identities, current transaction ID, and `same_transaction_only:true`. Issuer/redemption/reward-issued stay false. It is **not** full spend eligibility, a reusable signed permit, a one-use consumption receipt or an execution command. A future issuer must invoke this live inside its actual issuing transaction, retain all locks, run typed debt/eligibility reconciliation and coherent receipt/claim/coverage creation, and independently check installed gates. It must never persist this result as authority for another transaction.

## Exact lock matrix

Current owner session/account check precedes derived customer's `offline-claim-auth`→`offline-claim-profile` mutexes; actual link/Auth/consenting-session/customer row SHARE locks; contact table SHARE plus digest verification; exact `offline-financial-consent:<nonce>` mutex; exact `offline-reward-consumption:<preparation>` close fence; accepted `reward-offline-profile`→`offline-reward-reserve`→sorted original source invoice locks. No source/reward/invoice lock is acquired before claim identity. No shift is acquired. Customer financial withdrawal and link revocation acquire the same claim identity mutexes, so they serialize with the live checker; preparation close serializes at its nonce before releasing the hold. Actual refund writers keep shift→invoice. No opposite lock edge is introduced by this helper.

The original consenting session requirement is deliberately fail closed: sign-out/expiry before issuance invalidates that assent for this locked-hold use. Another fresh customer session can view its historical receipt, but cannot replace its immutable accepted-session evidence. A new explicit proposal/assent path is needed after expiry/invalidation; there is no automatic reuse.
