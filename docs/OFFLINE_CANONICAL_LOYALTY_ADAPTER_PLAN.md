# Offline customers in the canonical service-visit engine

Source proposal only · 14 November 2026. No migration, data, activation, application or capability change is included. Installation/readiness of the source files below must be confirmed separately by the coordinating agent. In particular, the new history reader and work kernel sources are not evidence that offline loyalty is enabled.

## Scope and invariants

Use the existing canonical `service_visits` engine for both authenticated customers and offline profiles. A visit is not a monetary point. Do not convert the legacy `business_loyalty_transactions` balance, invent opening rights, create Auth users for guests, rewrite customer/profile/earning primary IDs, transfer credits after linking, or create an independent guest credit ledger. Existing financial and entitlement history remains immutable. New owner policy versions and explicit channel activation govern future work only; all offline earning/spending capabilities start disabled.

An offline profile remains the owner of its credits when a reviewed app link exists. Linking grants a revocable, separately consented access path; it does not make the Auth customer the credit owner or merge two wallets. Overlapping program pools are displayed independently and never summed.

## Minimal unified schema and kernel proposal

1. Add nullable `offline_profile_id` FKs to the existing canonical credit, quote, redemption, claim and review tables. Relax only their existing `customer_id NOT NULL` constraints and add enforced XOR owner checks: exactly one real Auth customer or real offline profile. Existing Auth rows already satisfy this without updates. Define immutable owner accessors returning `(kind, id)`, not a bare UUID that could collide across namespaces. Cross-row owner equality must be enforced by guarded inserts/deferred proof, not client assertions. Private RLS/no client table grants remain.
2. Make booking/vehicle/date/time requirements conditional on real source kind, not universally nullable without checks. Add an immutable order-level source binding/snapshot for new work. Keep all existing FKs where they apply; the offline source must reference actual `offline_walk_in_subjects`, profile/car/service/branch and creator proof. Do not overwrite `booking_loyalty_policy_snapshots` or capture old work retroactively.
3. Parameterize allocation, refund sync, pool reading and eligibility by typed owner. The SAME existing credit/claim/redemption records and one-active-claim uniqueness power both adapters. Legacy Auth wrappers resolve `auth.uid()` and call this kernel. No arbitrary owner ID is accepted from an app without server reauthorization. Migrate all locking call sites together, preserving request→identity/owner→ordered invoice/claim lock order and shift→invoice cash/refund ordering; do not acquire a shift after taking an invoice lock.
4. Capture explicit future policy/version/channel/typed-target eligibility, activation and currently activated earning-rule binding on accepted work. Default offline channel false; activation must fail if completion, settlement, reversal, spend-consent, commission or recovery support is incomplete. Existing target Auth UUID lists never silently match offline profiles. Do not extend old configured programs to a new channel by implication.

## Authorization and free consent

For a linked customer, separate wallet-read and spend consent must name the actual offline profile/program scope. Call the live reviewed-link resolver under the same revocation/contact/session locks for options, quote, placement, wallet and receipt retrieval. Recovery may return only the already authorized actual receipt; link revocation prevents new financial dispatch and private detail disclosure. It does not move/revoke earned credits. If one person has Auth and offline credits, expose clearly separate typed pools until an explicit future cross-owner policy is approved; never add them together or allocate across both by accident.

For a customer without the app, the proposed FREE financial-consent mode is an owner-configured, DEFAULT DISABLED `independent_owner_in_person_approval`. This is operational trust backed by in-person attestation, not proof of phone ownership or remote OTP verification. It introduces no SMS dependency. Explicit owner policy selection is required before enabling it; no seed or implicit channel activation is permitted.

The exact flow is:

1. An active, branch-authorized cashier requests an immutable pre-issuance quote for the actual typed offline profile/car, branch, service and eligible program. Bind the exact credit/visit allocation, reward, gross/discount/zero amount due, four frozen rules, expiry and fingerprint. The unit remains `service_visits`; a generic request for “points” must not convert visits or legacy balances. Nothing is issued or consumed at this stage.
2. Show the customer the actual financial-consent notice and exact quote: visits to consume, benefit, zero customer charge, cancellation/refund rules, expiry and no change of credit ownership. Record the customer's explicit assent through the in-person workflow, with the staff actor recording it. Registration/history consent cannot substitute for this financial assent. Any changed subject, service, allocation, rule, price or expiry invalidates the assent and requires a new quote/consent.
3. A DIFFERENT active owner, authorized for that branch, independently rechecks original service evidence and in-person continuity and records a reasoned attestation approving that exact quote/fingerprint. The creator/operator cannot approve their own request, even if they are an owner. Phone number, intake UUID, plate, or possession/knowledge of an old enrollment code alone is insufficient. Record references to existing service evidence and bounded attestation fields; do not collect or store additional ID images.
4. Issuance revalidates customer assent, independent approval, current branch/actor authority, quote expiry, unchanged owner/policy terms, actual credit availability and any refund/review debt under the common locks. Approval authorizes exactly one bound quote, not future transactions or a transferable balance. Use immutable audit, one-use approval/consumption uniqueness, exact request replay, authoritative prepare/get/close/ack fencing and atomic invoice/claim issuance. Expired, altered, revoked or already-used approval fails closed without normal-money fallback.

An owner operating alone has no self-approval escape hatch. Display the operational constraint and keep guest redemption unavailable until either the customer independently approves through the linked app path below, or an independently authorized staff/owner arrangement satisfying the configured separation exists. Do not silently treat a second browser/session of the same actor as independent. The policy must state eligible creator and approver roles explicitly; current proposed in-person approver is an owner, not an arbitrary employee.

The alternative is customer self-approval through fresh confirmed Auth, the live owner-reviewed trusted link, and explicit wallet/spend scopes. The customer approves the exact bound financial quote as a separate actor; fresh-session/confirmed-email/contact/link evidence is checked again at issuance. History-read consent alone never permits this. The server must not silently switch between in-person and app consent modes, or reuse an approval from another profile, program, branch or quote. Neither mode transfers credits to the Auth customer, proves phone ownership, reissues enrollment secrets or creates Auth accounts for guests.

These are now the proposed implementable modes, rather than an unspecified future SMS/identity mechanism. They still require explicit owner policy configuration and the backend/concurrency acceptance gates below before any capability can become enabled.

## Settlement, refunds and commissions

Earn once only after actual completed service AND a trusted settlement the shared kernel can prove. The current trusted source is full cash sale; do not treat card intent/receipt upload or an unset future provider as settlement. Future trusted rails require separate server integration. A reward-covered zero invoice is not a cash payment and earns no new visit unless a future explicit policy and non-circular settlement model are approved (default excluded).

Refund processing must use actual refund-payment IDs and original earning reversal, independently of worker timing; same event replay is a no-op. For already consumed credits keep the frozen explicit `offset_future_visits` versus `freeze_for_owner_review` rules, issued reward honored, no retroactive customer charge. Cancellation retains frozen restore/forfeit choice and original expiry. New owner review actions must never edit original credits or financial receipts.

Worker commission is based on the frozen service gross BEFORE discount, including a reward-covered service. Reuse actual per-worker assignments/rates/N/gross/rounded amounts; heterogeneous shares remain NULL, never averaged or set to zero. Current typed Walk-in invoice proof requires invoice total=gross, discount=0 and reward_snapshot NULL (`20261114172315`, guard near lines 64–71; work-kernel replacement near lines 189–200). Therefore offline reward issuance cannot merely set total=0: it needs an explicit same-transaction coverage proof allowing `total + discount = frozen gross`, exact canonical reward allocation/consent, and the unchanged frozen commission lines. Commission settlement/posting timing for reward services must be explicitly defined in the shared HR earning path before activation; neither a zero invoice nor a fabricated sale may be used to bypass it. Preserve historical ledger and legacy service guard; no backfill.

Owner decisions first: future eligible channels/services/typed audiences; whether linked holders may view/spend offline pools; explicit independent-owner in-person versus linked-customer self-approval consent mode and role separation; reward-service commission recognition; reward-on-reward earning excluded unless separately designed. Record explicit versions with no seeded/default activation.

Refresh affected immutable guards deliberately for NEW inserts, never mutate old ledger facts. Rollback fixture must prove old Auth booking rows/functions unchanged, wrong-owner/cross-source rows rejected and no fabricated Auth/booking required.

C. Shared earning adapter: actual completed offline work plus trusted settlement; same outbox/reconciler/credit table, new future frozen policy/channel binding. Tests cover unpaid complete, paid received, excluded channel, preactivation, missing snapshot, targeted wrong owner, actual cash complete→one earn, duplicate workers/events, refund-before/after-worker, concurrent cash/refund/completion, bounded lock timeout and retry. Verify old rows and exact credit count.

D. Typed shared wallet/allocator/refund sync: one active claim per earning, frozen rule cohort/expiry, overlapping pools unsummed, linked live-proof+new scopes. Test link revocation/email/contact/session change racing quote/place; wrong profile, Auth/offline UUID collision, older-rule escape, offset/freeze debt, restore/forfeit and retries. No credit ownership updates during link/unlink.

E. Offline redemption issuer and consent: one actual quote→prepared command→allocated claims→zero covered invoice, frozen per-worker gross commission, exact durable retry/close/ack. Tests include missing/expired/replayed consent, operating-cashier/owner self-approval refusal (including a second session), missing customer assent or independent-owner attestation, expired/changed bound quote, phone/intake/old-code-only refusal, wrong branch/service/person, concurrent double spend/close and lost-response recovery, unique invoice, no cash event, no loyalty recursion, refund after consumption and reward-worker earning without fake settlement.

F. UI/capability activation only after backend gates: honest separate visit pools, exact frozen terms/expiry/consent, zero due plus gross/discount, actual staff commission remains private, no phone-only spend. AR390/EN1440 targeted tests and one isolated real local journey per supported channel; retain partial success rather than repeat financial fixtures. Default flags remain false until all applicable phases pass. No hosted changes or production seed are authorized by this plan.
