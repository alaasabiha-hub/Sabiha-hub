# Typed trusted-link history reader plan

Status: source-only design, 2026-11-14. No migration, RPC, reader grant or UI capability is implemented by this document. Existing `approved_pending_reader_bridge` remains truthful. The accepted AR390/EN1440 claim journey proves evidence review and revocation, not historical access. No production changes, Auth/customer/vehicle UUID rewrites, automatic merges or loyalty imports are proposed.

## Verified boundaries

`20261114165702_offline_customer_claim_review_records.sql` stores one immutable reviewed link per profile/account, with receipt/claim IDs, actual confirmed-email digest and confirmation timestamp, complete observed-contact-set digest, approving owner and first revocation timestamp. Active uniqueness is enforced separately for profile and Auth account. Claim approval alone deliberately returns history/wallet/reader flags false. Receipt continuity includes owner review; phone/name/plate matching is never authorization.

`20261114172315_offline_walk_in_service_and_frozen_commissions.sql` stores exact `offline_walk_in_subjects(profile_id,car_ref_id,order_id,invoice_id,registration_request_id,branch_id,service_id)` associations. Actual orders have `customer_id=NULL,booking_id=NULL`; historical identity and per-worker financial sidecars are immutable. A reader must follow these associations, not infer ownership from an invoice snapshot, phone, name, plate, generic null customer or registration actor. Received-only is not completed; current actual work and payment facts must be read separately.

Current `get_customer_booking_history` and public vehicle readers are Auth-customer paths. `get_my_reward_wallet` synchronizes Auth-customer canonical credits and does not support offline subjects. Existing `resolve_invoice_document` uses `can_read_invoice`; do not broaden that shared predicate for this slice. Invoice snapshots/command receipts may contain operational or worker data and must not be returned wholesale.

## Smallest complete read-only slice

Add a private authorization resolver and three typed customer RPCs, keeping existing account history intact. Public wrappers are invoker, authenticated-only, with default PUBLIC/anon execute revoked. Private definer functions have fixed `pg_catalog` search path, qualified objects and explicit current identity checks. No private table grants, broad RLS OR clause, owner/cashier escape hatch or service-role-without-user access.

Proposed contracts (not current APIs):

* `get_my_offline_history_context()` returns `{state, capabilities, cars, history_scope}`. States `available|not_linked|review_required`; never reveals another profile or candidate existence. Capabilities distinguish `linked_visit_history`, `linked_invoice_documents`, and `offline_car_reference_read` from false `vehicle_management`, `wallet_access`, `walk_in_loyalty_accrual`, `guest_redemption`. Cars are explicitly read-only reception references, not app-owned `vehicles`.
* `get_my_offline_visit_history(p_before_created_at timestamptz default null,p_before_order uuid default null,p_limit integer default 25)` returns `{state,items,next_cursor,capabilities}`; limit1..50, cursor pair validated. Derive the profile from caller, never accept profile/account/branch selectors. Order stable by immutable subject creation time and order UUID descending. Every item is a whitelist: `source_kind:'offline_walk_in'`, internal order/invoice references for typed RPC use, actual short invoice/work reference, branch friendly name, service friendly name, subject creation/arrival time, actual work status, car reception snapshot, immutable gross/discount/invoice face amount and currency EGP, current payment status and collectible amount. Include cancelled/refunded facts clearly; do not omit them or call unpaid work completed. No raw payment events, cash shift, operator IDs, notes, staff assignment/commission/rate/employment, enrollment/claim secrets, contact hashes or full stored JSON.
* `get_my_offline_invoice_document(p_invoice text)` accepts only an invoice linked through the currently authorized typed subject. Uniform unavailable error for unknown/foreign/revoked/disabled document. Return a versioned explicit customer document projection with immutable issuer/branch/invoice number/date, necessary receipt customer/car/service lines, amounts and recorded tax facts, plus separately labelled current work/payment/refund state. Preserve existing `tax_amount:null` / not-recorded semantics; no invented zero tax. Return no internal commission model/worker lines. Reuse `InvoiceDocumentScreen`/PDF rendering only through an injectable typed gateway after checking its exact supported schema. No general invoice token permission, signed Storage URL or public QR capability is granted.

`get_my_offline_history_context` must not return a profile UUID as an invitation to other readers. Car references expose only the caller's reviewed profile, and can supply opaque read-only IDs where pagination/UI needs them. Existing app vehicles remain a separate list; no automatic registration or plate reassignment. Deduplicate visits by subject order/invoice keys, never across phone/name matches.

## Authorization and revocation semantics

For EVERY RPC and every document/PDF fetch, require actual `auth.uid()`, an existing live nondeleted/unbanned Auth user and public customer, confirmed current email whose digest and confirmation timestamp exactly match the approved link, an active unrevoked link and actual approved claim/decision consistency, and unchanged full observed-contact-set digest. Never trust JWT user metadata, editable customer email/phone flags, cached claim outcome or possession of invoice/receipt UUID. Missing/stale evidence fails closed with generic `review_required`; no automatic link update. Owner approval remains historical evidence: later owner departure does not silently rewrite it; explicit revocation is the withdrawal mechanism.

Strict session invalidation is part of implementation review: validate JWT session against current `auth.sessions` where current project sessions supply `session_id`, rather than assuming user deletion invalidates a still-live JWT. Do not accept a forged missing session or service-role claim as a customer shortcut. Tests must use real authenticated sessions as well as role-forgery SQL.

Fresh post-revocation requests must fail immediately. For deterministic in-flight ordering, take the existing actor→profile advisory mutexes, share-lock the selected link and current Auth/session/public customer rows, and check the complete contact digest under READ COMMITTED. Recheck the digest after constructing the result; no table-wide contact lock is needed. A revocation committed before those locks denies the read; a read linearized first can finish, then revocation commits. Avoid repeatable-read stale snapshots by explicit isolation guard for the sensitive resolver. Document the lock order against current approval/revoke writers before coding; two-session tests must prove no deadlock. Keep locks only for bounded RPC assembly, never browser rendering/streaming.

No network design can retract data already delivered, a saved PDF or a request authorized before revocation. The app must not cache these results in SharedPreferences/localStorage/offline service-worker data; clear in-memory linked lists and documents on sign-out, identity change, review-required or revoke response. Use private no-store response handling where available. Do not claim revocation removes downloaded copies. Export generation reauthorizes before generating; avoid long-lived URLs bypassing the live check. Existing invoice QR remains the existing independently authorized route; the new customer reader must not enable a currently disabled document link.

## Historical and future scope

The proposed scope is existing AND future real walk-in subjects on the same reviewed immutable offline profile, including visits before link creation. This is purpose-specific access, not a backfill or ownership mutation. Add explicit history-access consent/version bound to the reviewed link before enabling it: present consent covers identity review while promising access unavailable until securely implemented; do not silently reinterpret it as blanket access consent. The owner must be able to see and resolve shared/family/recycled identity concerns before allowing this scope. A revoked/stale link requires fresh approved evidence and scope consent; consumed receipt does not become reusable.

Future subjects under the same profile qualify only by exact typed association. Newly appended contacts invalidate the existing contact digest and suspend reads pending fresh review. New car references under that profile do not themselves prove car ownership; display them as reception records. Car-only updates/transfers and conflicting ownership are unsupported. Legacy records without typed subject association cannot be recovered through phone matching; explicit audited migration/adjudication would be another authorized stage. No automatic attachment of unrelated older public customers/orders/invoices.

Guest visits do not earn canonical credits merely because a link becomes active. No synthetic visit counts, conversion to points, legacy balance merge, reward lots, allocation reassignment or redemption permissions. Current Auth-wallet RPC/booking reward rights stay unchanged. History may report an explicit `loyalty_earning_supported:false` per offline source; do not display zero as a verified balance or label count of visits spendable rewards.

## Privacy, changes and deletion

Changing the Auth email/confirmation or adding an observed offline contact suspends this reader until new review; changing public profile phone never transfers history. Distinguish app profile edits from immutable intake facts so customers are not told that editing app phone updates original receipts. Shared phone, reused plate, owner duplicate override, lost/stolen receipt and competing accounts remain review cases. Do not expose candidate profile IDs or contact lists.

Deletion/anonymization is a separate retention workflow, not `ON DELETE CASCADE` added by this feature. Current evidence/financial FKs can block Auth deletion and immutable records cannot simply be erased. Require a reviewed retention/legal policy before implementing deletion; this plan introduces no retention period or legal claim. A future request should revoke/suspend access first, preserve required financial/audit integrity, and separately handle permitted PII redaction/pseudonymization without rewriting issued invoices. Never promise automatic invoice deletion or silently retain new raw identity documents. No new image uploads required.

## Acceptance before enabling any capability

1. Isolated rollback fixture: genuine active approved link sees only its exact profile's pre-link and post-link typed subjects and reception cars; unrelated same phone/name/plate, another branch's foreign profile, failed/held/rejected/expired claims, unlinked account and forged JWT metadata cannot enumerate or fetch documents. Exact profile cross-branch subjects may be visible only when association is valid; branch alone never grants customer access.
2. Real Auth/live-session cases: confirmed email required, changed email or confirmation timestamp, banned/deleted account, missing public customer, revoked session and contact append all fail closed. Public profile phone edit cannot grant another profile. Missing or stale proof never leaks hashes/UUIDs of other candidates.
3. Two sessions: read versus revoke both commit orders; no post-revoke fresh read succeeds; contact append and Auth email change during read; pagination between revocation and next page; bounded lock timeout and no read/approval/revocation deadlock. No persistent reader transaction/payload caching.
4. Document proof: exact order/invoice/subject/branch coherence, document-link disabled, foreign UUID/token guessing, duplicate invoice associations, void/refund/payment changes and received work status; immutable invoice content unchanged. Safe whitelist excludes salaries, rates, internal notes, shift/events, secret/digest/contact evidence. PDF uses same gate and whitelisted payload, with truthful recorded-tax and no fake paid/reward label.
5. Car/history isolation: multiple reception cars, future same-profile car, same plate on foreign profile, inactive/hidden service and branch still display truthful historical snapshots without leaking broader catalogue or granting booking/vehicle edit. Deterministic cursor, maximum limit, no duplicate/missing order at equal timestamps.
6. Wallet invariance: linking/reading/revoking adds no earned/reversed/spent credits, no legacy points, no Auth/public vehicle/customer/booking/payment rows and no invoice snapshot revisions. Existing booking history/wallet behavior remains byte-for-byte for old fixtures.
7. AR390/EN1440 actual Flutter: separate previous reception history tile enabled only after successful reader context, real old invoice/PDF access, clear unsupported-wallet wording, revoke/identity change clears visible data and future opens denied. Test code/receipt secrets absent from reader payloads, logs/screens/cache. No claim quota resets or new Auth users.
8. Before/after all preexisting public/private row hashes, old invoice snapshots and document counters unchanged during rollback acceptance; local advisors and static function checks pass. Actual acceptance retains only explicitly approved QA audit; no production call. Root applies/tests, not this document author.

## Delivery sequence

First implement private resolver + typed context/history + safe document projection and isolated tests; capabilities remain false until all three paths pass. Then integrate a separate linked-reception-history UI/PDF adapter and actual Auth/browser revocation acceptance. Flip only tested reader-specific flags in a follow-up; preserve unrelated wallet/redemption/accrual flags false and existing claim receipts immutable. No generic `can_read_invoice` widening or app history promise before that acceptance. Shared capacity/work progression and guest loyalty are independent stages.

## Source implementation prepared (not applied or accepted)

CLI-created `20261114185540_offline_trusted_history_readers.sql` implements the proposed four public invoker APIs (including `accept_my_offline_history_scope(p_request,p_consent)`). Acceptance is controlled by a private `offline_history_runtime.enabled` row initialized FALSE with no client grants or activation RPC. Root's rollback acceptance can enable it only within the rolled-back test transaction; a separately reviewed acceptance follow-up is needed for persistent enablement. Existing immutable claim receipts and shared invoice/QR authorization are untouched. Context returns `consent_required`, `acceptance_pending`, `available` or generic `review_required`; data RPCs use the same generic 42501 denial for unavailable/foreign identity/invoice. Fixed scope version is `offline-history-v1`; exact bilingual notice comes from context, consent is bound to the current reviewed link, and exact request UUID replay still rechecks current identity/link. No additional owner approval step is introduced.

Actual lock design: use existing claim-auth then claim-profile advisory order (same as approval/revoke), then share-lock link/Auth session/account rows; enforce READ COMMITTED and20s lock bound. No global contact lock or new contact trigger. A profile-lock contact trigger could deadlock existing approval's profile-lock→contact-table SHARE order against an INSERT's earlier table RowExclusive acquisition. The digest is checked on authorization and again before return; an append committed before the final check denies, while a later append invalidates subsequent requests. Readers and revocation serialize under existing actor/profile mutexes; already delivered data remains irrevocable.

Session validation checks `auth.jwt().session_id` against persisted `auth.sessions.id/user_id` and explicit `not_after`, plus current actual Auth email confirmation/deletion/ban. Missing/foreign/removed/expired sessions fail closed; editable metadata is irrelevant. [Supabase session documentation](https://supabase.com/docs/guides/auth/sessions) recommends checking persisted session presence for sensitive actions. Row presence does not independently enforce every configured inactivity timeout; delayed cleanup and session policy remain Auth-server concerns. Refresh-token revocation alone is not mislabelled guaranteed access-token invalidation.

The safe document projection is structurally compatible with current PDF snapshot fields, excludes internal worker/commission/evidence JSON and preserves recorded-tax truth. It includes the existing own invoice token/origin as immutable reference, but `qr_reader_bridge:false`: the generic QR reader still has its existing independent authorization and is not made usable for offline links by this slice. Later typed UI/PDF gateway must not promise working linked QR access. No UI route or PDF gateway was changed here.

`supabase/tests/offline_trusted_history.sql` is an unexecuted isolated rollback fixture using existing Auth accounts, transaction-only test sessions/config, real intake→claim→owner approval→typed received invoice paths. It covers consent/idempotency, disabled gate, session/missing/foreign/expiry/removal, changed email/confirmation, ban/deletion, contact append, pre/post-link history/pagination, safe document fields, foreign/unknown/disabled invoice, cancellation/revocation and no financial/reward mutations by reads. Static checking, actual rollback execution, concurrency lock-order tests and real authenticated/browser acceptance remain ROOT-CONTROLLED and pending; no pass is asserted.

## Actual local harness prepared, execution pending

`tools/offline_trusted_history_validation.py` defaults to PLAN and requires explicit `--execute` plus root's exclusive local DB window. Syntax compilation passed; no actual run is asserted. It checks the named prior QA employment journals and unchanged final hashes, never creates/updates salary terms. It uses two existing confirmed accounts only when each has room for one legitimate new claim and no active link; no quota resets or account creation. One-account availability produces an explicitly incomplete second-race result. Case A creates its received invoice before linking; case B after linking. Fixed scope, own history/documents, cross-account denial, rollback-only contact append and a dedicated newly logged-in session's local logout are tested. Both real read/revoke commit orders and the actual20s lock timeout/same-nonce retry are included.

Failure cleanup settles the exact owner approval/intake/walk-in nonces before case-ID lookup, then revokes only validated QA links, voids only unpaid same-branch QA orders, acknowledges commands, hides only new setup and restores runtime disabled. Received/void booking-less work must leave the outbox empty. The harness never drains jobs; any unexpected pending event fails acceptance and is retained for root review. Proof compares every preexisting public/private row, Auth identity fields and borrowed HR hashes, allowing only the exact new invoice numbering delta and whitelisted new QA/audit rows. Raw enrollment secrets, JWTs and HTTP bodies are never written to proof/state/logs/traces. New session rows are Auth-server-issued; the logout targets only the dedicated new session.
