## Narrow source component now drafted

CLI migration `20261114222304_offline_service_visit_wallet_read_scope.sql` adds only an independent disabled read gate, immutable read consents, private snapshot projection and two authenticated invoker wrappers:

* `get_my_offline_service_visit_wallet()` derives the profile through the existing live `resolve_my_offline_history_link` (actual persisted session, current confirmed email, actual owner-approved claim/link and contact proof, revoke mutex order). No profile/customer selector is accepted. States: review_required, consent_required, acceptance_pending, available_read_only. It never calls the Auth sync/allocator or writes credits/claims/debt.
* `accept_my_offline_wallet_read_scope(p_request,p_consent)` requires exact fixed `offline-wallet-read-v1` AR/EN notice and acceptance, bound to the actual current link/actor. Exact UUID retry rechecks current evidence/revocation. History and registration consent are insufficient. No payment/spend permission is granted.

The independent `offline_visit_wallet_runtime.read_enabled` starts false with CHECK(not read_enabled) and no public enable function. Root may replace that CHECK only after scoped local/static/AR/EN read acceptance; this is not another earning gate or scheduler. Existing earning runtime stays locked false. Consent may be recorded while read acceptance is pending without disclosing balances.

Projection uses the SAME canonical credits, actual `reward_credit_refund` evidence, reversals, frozen overlay/activation and original rule binding. Only cohorts with actual credits owned by this profile appear; it does not list unrelated targeted programs. Cohorts are separate by overlay/activation/policy/rules and capped100 with a truncation flag. Names are frozen own-program names; full policy/rules/audience/facts JSON, profile IDs, staff rates and secrets are not returned. No mutable latest configuration reinterprets old rights.

Outputs distinguish lifetime earned, ledger reversals and effective actual refunds including pending async reversal. Per-cohort recorded unclaimed-valid visits are DESCRIPTIVE, not a spend promise. `global_spendable_balance` and `debt_adjusted_spendable_visits` stay NULL, overlapping pools unsummed, redemption/allocation/debt resolution/points conversion false. No zero profit/points/currency conversion is invented. Pausing earning does not itself remove read rights; only its own accepted read gate and current identity/read consent authorize viewing. Auth and offline wallets remain visibly separate in future UI.

## Financial authority modes still to implement

Linked app customer: actual fresh Auth/session+current approved link on EVERY wallet/quote/place/recovery, independently bound read scope and quote-specific spend consent (owner/profile/program/rules/price/expiry/allocation/purpose). History consent, a persisted old quote, known receipt or operating cashier's checkbox is not spend authority. Revoke/email/contact/session change denies new spending but does not rewrite credits or already issued receipts.

Guest without an app link: no public customer reader currently exists. Future owner administrative review must be explicit active-owner, scoped to actual reception/profile and audited purpose, not phone lookup. **Independent in-person owner authorization for SPEND** is separate: explicit configured policy, actual customer assent/continuity evidence, one-use quote-bound short-lived attestation and owner different from operating cashier by immutable Auth identity (another session is not independence). No cashier self-approval, implicit read-consent reuse or phone-only claim. These modes are design dependencies, not implemented capabilities. Read-only scope does not establish that a guest can redeem.
