## Exact occupancy semantics

There are two separate truths:

- **Physical occupancy now:** a real source that has started and has not completed continues to occupy one configured resource unit, even after its expected end or across midnight. `in_progress` and `quality_check` occupy; `completed`, `delivered` and cancelled-before-start do not. Overrun never silently frees a bay. Quality check remains inside the same resource until actual completion; no unconfigured off-bay capacity is assumed.
- **Planned occupancy:** each real booking reserves its existing frozen service interval. A newly started typed walk-in has an actual start and an expected end computed from the already frozen real duration, not a fabricated booking. Future booking checks count its known expected interval. An overrun whose expected interval has expired does **not** reserve every future time indefinitely: future slots are planned availability and every real start rechecks physical occupancy. No promise that a future appointment can start despite an uncleared physical overrun. Queue/context must label this distinction and surface active overruns.

For a start at server time `T`, calculate the maximum simultaneous occupancy across `[T,T+frozen_duration)` from other planned booking windows and known started walk-in windows. At `T` additionally count every physically active source whose planned/expected end has expired (carryover), without double counting a source already represented by a window. Start requires both the physical point count and the planned-interval peak plus this source to fit configured capacity. Known overrun carryovers remain present throughout this newly admitted interval for conservative admission; they disappear only on actual completion. This does not rewrite their future expected end or claim their unknown real completion time.

For creating/rescheduling a future booking interval `[A,B)`, retain existing booking maximum-overlap logic and add only known walk-in expected intervals overlapping it. Active overrun evidence is returned as a warning/recheck requirement rather than converted into an infinite reservation. Do not invent a fixed grace period or claim an estimated end is actual completion. A later walk-in start cannot steal a real booked interval already using all bays.

Capacity is `public.business_branch_resources.capacity` for the source's actual frozen `resource_key`. Missing/inactive/ambiguous configuration fails closed. A missing duration or resource is not guessed from a service name. An already in-progress booking without a new typed start record is still physical occupancy from its current booking/order state; it is flagged as legacy/unknown actual start rather than assigned a fake start timestamp. Unclassified active booking-less legacy service orders have no trustworthy resource snapshot: block new physical admission for that branch with `unclassified_active_work_requires_review`, rather than assigning them an invented bay. Future planned bookings are not financial/history conversions.

## Source identity and double counting

Private new `service_resource_spans` uses typed `(source_kind,source_id)` with `booking|walk_in`; an existing booking plus its linked business order is **one** physical service, never two. Booking physical status is active if the actual booking is `in_progress` or its one unambiguous linked service order is `in_progress|quality_check`; multiple linked service orders fail closed. Walk-ins use the immutable `offline_walk_in_subjects` binding and actual business order. No fake booking, customer UUID substitution or new Auth record.

New spans capture actual server start, actual frozen branch/resource/duration and expected end. Start fields are immutable. Completion closes the span once, under an actual authorized work-event witness; no deletion, reactivation or later start rewrite. Original financial subject/worker/rate/invoice facts remain immutable. Existing active legacy booking rows need no financial or identity backfill to be counted conservatively.

## Locking and shared admission

Reuse the exact existing resource advisory key `branch_uuid::text || cairo_date::text || resource_key`, seed0. Future booking checks lock the affected booking day. Physical start/finish locks current Cairo day; when the source's scheduled/start day differs, acquire distinct relevant day keys in sorted date order. This serializes admission/completion against same-day booking creation, including overnight carryover. Config edits keep their existing branch config lock/row protections.

Use READ COMMITTED, refresh source/occupancy reads after admission mutex acquisition and bound lock_timeout20s. Do not lock other services' booking/order rows when calculating occupancy; read their committed state under the shared mutex to avoid resource↔foreign-row deadlocks. Existing row-update triggers may already hold their own row. A start/cancel command never takes a cashier shift lock after order/invoice locks. Completion does not manufacture a payment/refund or change invoice money.

One source's idempotent start replay must not create a second span. Same request UUID with changed actor/source/expected state fails. Both competing starts at capacity1 acquire the same resource mutex: exactly one may enter. Booking creation versus walk-in start uses that same key, so their post-lock checks cannot each admit the same final unit from stale snapshots.

## Work kernel follow-up source — atomic paired completion

Source only: `supabase/migrations/20261114185821_shared_service_work_transition_kernel.sql` and `supabase/tests/shared_service_work_kernel.sql`. Applied foundation183930 and received-only72315 stay unchanged. The new migration copies the current financial guard and changes only its typed work-status witness predicate; all invoice, line, assignment, commission and document guards remain. It installs no queue/UI and flips no global readiness, tax/ETA or loyalty flag.

The reviewed implementation uses **atomic paired completion**, superseding any suggestion that a closed span alone should override an actively quality-checking companion row. An actual booked order must reach `quality_check`, its single same-branch booking must be `in_progress`, and all currently required before/after inspections must be approved. The canonical command locks both rows, prewrites immutable witnesses for both, updates both to completed in one transaction and releases the physical span once. Direct booking-only completion while the order is quality-checking, and direct order-only completion while the booking is in progress, both fail closed. No order graph step or required inspection is skipped. Legacy direct completion is accepted only when the other row is already completed/certified (or there is no linked order); ambiguous pairs require management reconciliation.

Five authenticated invoker/private definer RPCs:

- `prepare_service_work(p_request uuid,p_order uuid,p_expected_status text,p_next_status text,p_reason text)` stores exact request and a private immutable branch/booking/assigned-staff source snapshot. Reason is5–500 characters. Actual graph is received→in_progress→quality_check→completed→delivered. Actual currently assigned active branch staff may perform the first three actions; delivery requires active owner/branch manager. Cashier status alone is not work authority. The source must be a real typed walk-in or one real unambiguous booked service order; no fake booking/Auth.
- `place_service_work(p_request uuid)` executes only the actor's saved command under the request fence. Current role/assignment and expected state are rechecked, and source/dispatch changes return40001 before locking a different linked row. Canonical booked APIs acquire their pair mutex before order+booking row locks, then canonical vehicle/offline-car, branch and exact resource mutexes. Both source rows are held before paired writes; legacy row triggers never lock a foreign work row. No money or assignment is edited by work execution.
- `get_service_work_command(p_request uuid default null)` recovers own prepared/unacknowledged success first, including after lost UUID discovery response. It returns exact saved input and immutable own performed-action receipt. Current work/booking/physical state is overlaid only while current work authorization still holds; otherwise `current_state_available:false` and no updated old-job data. Active former assignees can recover/fence their **own nonce** without gaining customer/profile/invoice/photo/history access. Human reference is a real unique invoice display number or booking/short legacy reference, never a displayed full UUID.
- `close_service_work_command(p_request uuid)` closes a prepared request, preserves a committed success, or creates an own absent-request tombstone under the same mutex. Closed tombstones are outside the unresolved unique index, so absent A can be fenced while distinct own command B remains unresolved. No old received-stage financial index is rewritten. An active staff member may safely close their own stale nonce after unassignment; this returns no current old-job data.
- `ack_service_work_command(p_request uuid)` acknowledges only own known final receipt; prepared actions cannot be acknowledged into disappearance. Every command/action row is retained. Clients must persist request UUID before prepare, freeze after ambiguous transport, recover the server payload/result and never rotate identity until known resolution. No UI is claimed by this backend stage.

Resource clocks are captured after locks, not before a wait. Locks include current/adjacent business days plus actual scheduled/start days in sorted order, using the same existing `branch||day||resource` key. Adjacent-day keys cover midnight/carryover during the short transaction; they are locks, not future reservations. A larger day jump fails for refresh. Canonical Auth vehicle/offline car-reference mutexes prevent simultaneous starts for the same actual typed car; plate/phone is never identity proof. Physical quality check keeps the span open; expected end/overrun/midnight never auto-release it. Actual witnessed completion releases it once. Service cannot restart after that certificate.

Direct authorized booking starts and linked-order starts use the same admission hook. A raw linked order cannot independently start a still-confirmed booking; use the paired API or start the booking first. Observed already-active legacy booked work with unknown original start may continue without inventing a start timestamp. Unclassified new legacy service starts fail closed; existing actually active legacy work may finish its original assigned-worker graph, resolving its physical-review blocker. Active cancellation is not a silent release route: it requires a future explicit management stop workflow. Received unpaid cancellation keeps its existing canonical route.

Inspection-required offline starts remain blocked; if the owner enables required inspections during an active offline service, completion also fails closed until a truthful typed inspection route or explicit authorized policy resolution exists. The code never disables that setting. Branch closure blocks new admission but does not prevent authorized safe completion of already active work. Existing booked inspection checks are preserved and also enforced on linked-order completion. Existing canonical booking earning is not reconfigured; new walk-ins still have no booking/earning binding and cannot mint visits/points or use legacy loyalty fallback.
