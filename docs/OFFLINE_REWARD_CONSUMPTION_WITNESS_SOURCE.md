# Private offline hold-consumption prerequisite

Source-only additive migration `20261115022019_private_offline_reward_consumption_witness.sql` follows the accepted private holds in `20261114225604`. The CLI created the migration. It has **not** been applied, compiled against PostgreSQL or exercised by the author. No database, Auth, Flutter or runtime gate changes were made. No SQL pass is claimed.

## Why this boundary

The accepted `fence_offline_redemption` and `fence_offline_refund_review` triggers still reject typed offline redemptions/debt. The current `guard_offline_walk_in_finance` in work kernel `20261114185821` requires `total=gross`, `discount=0`, `reward_snapshot=NULL`, and exact frozen per-worker commission lines. A real offline benefit cannot be issued merely by inserting a zero invoice or fake cash event. Consumption requires both typed refund/cancellation reconciliation and honest commission recognition, which are not installed. These fences remain unchanged.

The new records are preparation evidence only. The witness's quoted `amount_due=0` describes the intended covered benefit; it is not an invoice, settlement, customer consent, approval, credit conversion or permission to spend. Every response advertises consumption and issuer disabled. No public RPC or grant is added.

## Exact private contract

* `prepare_offline_reward_consumption(request UUID, reservation UUID, fingerprint text)` requires the current actual owner/session through the accepted reservation guard. Only the hold's original operator can prepare. The nonce binds the exact reservation and 64-character quote fingerprint. One immutable preparation exists per hold; a different nonce cannot create a second preparation for it.
* `get_offline_reward_consumption_preparation(request UUID)` rechecks current owner/session before cached recovery. `absent` is explicitly nondefinitive. `prepared` returns the exact stored payload/witness and a freshly checked `hold_current`; the latter is **not** a spending capability. Expired/refunded/released/changed holds yield `hold_current=false` without rewriting historical evidence. Unexpected errors are not disguised as invalidity. `closed` is definitive for this preparation nonce.
* `close_offline_reward_consumption(request UUID, reason text)` records a permanent actor-bound tombstone even if prepare was never seen. A late prepare cannot pass it. If a preparation exists, close releases only its exact unconsumed hold using the existing audited release writer and keeps the original witness. Repeated close does not rewrite the original reason/time. There is no action that reopens a preparation or consumes a claim.

`offline_reward_consumption_preparations` and `offline_reward_consumption_closures` are private, RLS enabled, immutable under update/delete, and revoked from PUBLIC/anon/authenticated/service_role. No raw phone, consent, secret or customer-email fields are introduced. Internal helper functions are likewise ungranted. No historical record is rewritten.

## Locks and source proof

All operations require READ COMMITTED. The global preparation nonce precedes the accepted `reward-offline-profile:<profile>` then `offline-reward-reserve:<reservation>` mutexes. Source invoices lock in invoice-ID order; no cash shift is acquired. Close also locks original source invoices before audited release, allowing an already-committed cash refund to determine the terminal release classification. The existing cash path's shift→invoice order remains untouched.

After invoice lock waits, preparation rereads actual active reserve claims, their exact IDs/earning set, owner/channel/quote association, original hold expiry, actual refund payments and canonical reversal evidence, frozen allocation terms, current actual reward-service price/availability and active branch. The immutable witness includes exact quote/rule/policy/channel/service/car/profile IDs, fingerprint, original expiry, allocation and terms, gross and exact claim IDs. Global existing active-claim uniqueness remains the sole credit-occupancy constraint. No parallel credit ledger, scheduler or allocator is created.

A replay can return its original witness with `hold_current=false`. Closing another preparation for the same hold is impossible because only one exists. Releasing the underlying hold through the accepted existing release API does not erase the witness; get then reports it unusable. Idle expiry is not swept here. No fabricated clock or production test bypass is supplied.
