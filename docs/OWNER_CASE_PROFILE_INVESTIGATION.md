# Owner case-scoped profile investigation — source-only

This is the first missing seam for a customer who lacks the old receipt reference. It provides **owner investigation only**, without a proposal, canonical claim, approval, link, enrollment receipt, credit transfer or customer candidate API. Existing IDs, foreign keys, historical rights, Auth and role rules remain unchanged. Phone matching locates possible files; it is never identity evidence.

Migration `20261115012957_owner_case_profile_investigation.sql` adds:

* `search_visit_recovery_candidates(p_query UUID, p_case UUID, p_purpose TEXT, p_plate TEXT nullable, p_limit INT default10)`: actual current owner/session, active `awaiting_matching`/`more_info` case, and unchanged confirmed requester identity. Null plate derives the exact normalized phone from the case's current registered account **after** fingerprint verification. There is no arbitrary phone input. An explicitly entered exact plate can locate a file with a different old phone. The algorithm and length/control limits are the existing applied165824 intake algorithm, matched against existing `plate_key`; no fuzzy/wildcard or directory search is introduced. Results are deterministically capped1–25. An additive plate/profile index supports exact lookup; phone lookup reuses the existing contact index.
* `get_visit_recovery_candidate(p_request UUID, p_query UUID, p_profile UUID, p_purpose TEXT, p_plate TEXT nullable)`: the issuing owner must own the query, the profile must be in its bounded recorded result, and the current criterion/case identity must still match. The original case is derived from that immutable query. A known unrelated profile UUID is insufficient, even for this owner-scoped endpoint. The final detail predicate and whitelist projection run in one READ COMMITTED statement snapshot; a changed or missing criterion yields the same unavailable response and rolls back any new audit receipt.

Both return only whitelisted actual file facts: profile reference/name/time, original branch, bounded current recorded contacts with their **observed_unverified** status, bounded car references and recorded snapshots, real receipt existence, whether any receipt was previously linked, active-profile-link and active-requester-link flags. List child arrays cap5; detail arrays cap25, with explicit truncation flags. No secret/hash, Auth email, invoice/document token, visit history, balance, arbitrary JSON or candidate audience list is returned. Receipt existence is not receipt usability; ever-linked evidence remains consumed even after revocation. Every result explicitly reports identity proof, nomination and linking as unavailable/false.

New private immutable query and detail-read records capture owner, case, time, explicit purpose, criterion/payload hashes and the exact bounded selected profile IDs. Raw search phone/plate is not persisted in the audit records, and no PII response snapshot is cached. New request UUIDs distinguish investigations; same UUID with changed criterion/purpose/limit rejects. Replay rechecks current authorization/identity/membership and reprojects only the original recorded candidate IDs—never silently adds newly discovered candidates. Use a new query UUID to investigate fresh matches. Audit insertion is the only write in these read endpoints.

Nonce mutex comes before current owner/session locks, then requester identity share locks before case row share lock. No canonical claim/profile mutex or global contacts-table lock is acquired. Return rechecks current owner/session and case identity; a caller waiting on a lock cannot rely on an earlier role/session check. Protected share locks serialize identity/status changes as existing sensitive readers do. Old row mutation and query-audit deletion are forbidden to clients; all tables are private, RLS-enabled and ungranted. Only the two narrow invoker RPC wrappers and their explicitly gated private implementations are executable by authenticated callers; anonymous/service-role/private helper access stays revoked.
