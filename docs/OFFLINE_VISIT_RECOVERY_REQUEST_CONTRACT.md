# Previous-visit recovery orchestration: additive contract

15 November 2026. Design/source review only. Complements `OFFLINE_VISIT_RECOVERY_REQUEST_PLAN.md`; no migration, application change, database call, test or build accompanies it. The accepted claim/link/owner-command and actual history AR/EN PDF/QR proofs remain the baseline. The disabled owner service-visit foundation (`20261114211249`) and unapplied shared offline kernel (`20261114215603`) do not implement this request workflow and must not be duplicated or activated by it.

## Reuse boundaries verified in source

* `request_offline_customer_claim(p_request,p_receipt,p_secret,p_mode,p_consent)` is the ONLY existing customer claim creator. Its immutable `offline_claim_requests` stores proof snapshots/hash, not a recoverable secret. Preserve actual confirmed Auth/customer checks, live contact/email evidence, expiry, actor/receipt quotas and original/lost-secret modes from165702. `get_my_offline_customer_claim(p_request)` already derives ownership and returns uniform unavailable for foreign/unknown IDs; it rechecks current identity. A generic verification failure must not become an approvable recovery case.
* `prepare_offline_claim_command`, `get_offline_customer_claim_command`, `close_offline_claim_command` (171803) already provide actor-bound exact-payload owner recovery and permanent global nonce fences. Their supported kinds are EXACTLY `decide` and `revoke`. Reuse these actual APIs for canonical decisions/revocation; do not send a new case-action kind to the existing normalizer or weaken its allowed keys.
* A decision payload remains `{p_claim,p_decision,p_reason,p_evidence_type}` with required reason10–500; `approve_exception` uses `in_person_original_service_documents` or `in_person_independent_continuity_witness` and only `lost_secret_review`. Other decisions require null evidence type. `approve_with_secret` still requires the actual proof. Owner permission is current server `active_staff_role()`, never editable JWT metadata. Only `decide_offline_customer_claim` may insert a trusted link; the case system never writes that table directly.
* `offline_customer_trusted_links` retains profile/Auth/receipt/claim, confirmed-email/contact digests, original approver and first revocation. Linking does not rewrite customer/profile/order/vehicle IDs, move balances or grant rewards. The185540 history resolver/scope and191243 typed invoice reader remain authoritative on every history/PDF/QR access. History consent is separate from case/claim consent.
* `customer_order_notifications` (20261112202245,36–43) has non-null real customer and order FKs and unique(order,status). Reuse its existing UI host, not its storage for non-order requests. The order dispatch Edge Function and marketing recipient tables are not a generic inbox or identity proof. No fabricated order or claim UUID in an order FK; no FCM/SMS/email/marketing dependency is required for this feature.

## Proposed schema, no identity engine replacement

All additions are private, RLS-enabled, no direct client/service-role table grants; narrow guarded public RPC wrappers call private implementations with fixed search paths. Proposed names below do not exist yet.

`visit_recovery_cases`: case UUID PK; claimant UUID FK to the actual `public.customers(id)`; status/version; own submitted details/notice snapshot; created/updated/expiry times; nullable current canonical claim FK. Partial unique(claimant) WHERE status IN(submitted,under_review,awaiting_customer_evidence,claim_pending) enforces one open case. Terminal cases are retained. A confirmed Auth user without a real customer row cannot use a fabricated row to bypass this constraint.

`visit_recovery_case_events`: append-only event UUID, case FK, unique(case,version), actor UUID/type, action, bounded permitted public message, separate private owner note, optional actual canonical claim/decision/revocation IDs, proposal/version. No secret, password, ID images, balances or guessed historical visits. A monotonic case projection may change only with an actual matching event in the same transaction; old events/proofs never change.

`visit_recovery_receipt_proposals`: immutable proposal UUID/version, case, actual existing receipt/profile binding, contact digest and evidence references, proposer/time/expiry. These are investigation proposals, not links or financial consent. Customer projection exposes only the selected actual receipt reference and a minimal masked explanation after owner proposal; it never lists candidates or hidden contact sets. No legacy profile without a canonical enrollment receipt is silently enrolled.

`visit_recovery_action_commands`: durable exact normalized commands ONLY for new case orchestration actions. Store caller, case/version/action/server payload, open/succeeded/closed, acknowledgement time and immutable terminal receipt; stable UUID-only client persistence and authoritative prepare/get/close fences. This does not replace171803 or create a second identity approval engine. Case commands must reject UUIDs already used in the canonical owner-command family, and canonical decision commands must not be nested under a case-row lock. Final design must audit both-family collision/lock guards before coding.

`app_inbox_events` and `app_inbox_reads`: generic private transactional in-app transport. Event binds actual case-event/version, unique recipient customer UUID OR current-active-owner pool, fixed bilingual template/version and minimal source reference. Read receipts unique(event,user), monotonic read_at. Owner-pool authorization is evaluated at read time; former staff lose access. No client-supplied recipient, free-form push content, profile data or invoice tokens. This single inbox can host later transactional sources without altering order notification history/push state.

## Approve, more information and reject

Owner UI offers familiar actions but maps them to existing authority. With an attached pending canonical claim: approve uses171803 `decide` + existing canonical decision RPC; more information uses canonical `hold` with explicit bounded customer task in the new case event; reject uses canonical `reject`. Approval button cannot operate without an actual unexpired canonical claim and valid original-secret or independent in-person exception proof. A phone/profile candidate match never enables it. An investigation with no usable receipt supports only more information/proposal/rejection, not approval.

Do not add an `approved` Boolean writable on the case. Case `resolved` is projected from an actual canonical approval receipt. Canonical rejection projects rejected; hold projects awaiting_customer_evidence. Legacy direct canonical decisions and prepared-command paths must run the SAME narrow additive event/inbox hook, once per actual decision request UUID. A case-level reject must not leave an attached canonical claim pending and independently approvable: it must use the existing canonical reject flow. Any withdrawal with a still-live canonical claim needs an explicit canonical freeze/expiry bridge before being supported; default fail closed rather than creating a terminal case with a usable pending proof.

For receipt-less investigation, owner selects a real candidate only after bounded audited evidence lookup and original-service/in-person continuity verification. Customer explicitly confirms that immutable selected proposal and CURRENT claim consent. Then existing lost-secret claim/owner exception approval runs normally. Never manufacture a replacement secret, take phone matching as proof, relabel car references as legal ownership or revive a revoked/consumed receipt. Existing identity conflicts/expiry/revocation remain authoritative, including actions initiated outside this new case UI.

## Atomicity and lock discipline

Existing canonical owner path acquires `offline-claim-owner-command:<nonce>` then decision/revocation nonce, then `offline-claim-auth:<claimant>` then `offline-claim-profile:<profile>`. Preserve that order. A decision/revoke hook appends case event/inbox AFTER those existing locks; no wrapper may hold a case row and then call canonical approval/revoke. All orchestration-only writers must be designed against this order before adding expected-version locks. Claim attachment reads proposal optimistically, calls canonical creator under its existing locks, then locks/rechecks case/proposal/version and rolls back everything on mismatch.

Append case event, case projection update, exact command receipt and promised inbox events in one transaction. Notification failure rolls back the action. Replaying canonical approve/revoke/hold must not duplicate an event, consume a new claim or send another notification. Revocation does not rewrite old approved messages: append a current access-ended event and let protected readers deny immediately. Notifications never bypass live-reader authorization.
