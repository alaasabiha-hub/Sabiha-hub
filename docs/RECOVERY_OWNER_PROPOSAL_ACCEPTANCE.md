## Owner APIs

`prepare_visit_recovery_proposal(p_proposal UUID,p_query UUID,p_profile UUID,p_evidence_type TEXT,p_reason TEXT,p_attested BOOL,p_plate TEXT nullable)` accepts only an issuing owner's recorded bounded candidate, unchanged active case identity, same exact criterion, real unused enrollment receipt, no active conflicting identity and no existing mapped claim/open accepted proposal. Phone match is never sufficient: true explicit attestation and one of the existing independent in-person evidence types is required. Reason is10–500 characters. It freezes case email/phone/confirmation, historical contact-set digest, real receipt, evidence and both bilingual consent notices. Security TTL is24h, matching the existing claim-review interval; it is not a reward/labor policy default. Same nonce requires identical request hash, including raw plate input; no raw plate is stored in the proposal itself.

`get_visit_recovery_proposal(p_proposal)` returns only the issuing current owner's prepared terms and state. `close_visit_recovery_proposal(p_proposal)` permanently fences late prepare/accept for that proposal even if prepare has not arrived. If acceptance already committed, its accepted/review-required outcome wins; close cannot cancel a canonical claim/link. States are open, accepted, review_required, closed, expired, unavailable or absent. Absent is unconfirmed. Owner proof check uses actual live session/role, never JWT metadata.

## Customer APIs (no prior receipt UUID needed)

`get_my_visit_recovery_proposal(p_case UUID)` discovers the latest proposal for the actual own case. It returns case_id, state, proposal `{proposal_id,expires_at}` or null, frozen proposal/canonical notice versions and AR/EN text, own acceptance_request_id if any, approval_required:true and link_created:false. With no proposal, the same two fixed flags are included. There are **no** preapproval profile/receipt IDs, names, contacts, cars, owner reasons or old history. A changed requester identity is rejected, not quietly rebound. An accepted request reference is the caller's own canonical claim UUID, not the old receipt.

`accept_my_visit_recovery_proposal(p_request UUID,p_proposal UUID,p_consent JSONB,p_claim_consent JSONB)` requires BOTH exact `{accepted:true,version,text,language:'ar'|'en'}` objects as displayed. Proposal version is `visit-recovery-proposal-v1`; canonical version remains `offline-claim-v1`. Each chosen text must match the proposal's frozen corresponding notice. The unchanged creator independently validates its current canonical notice; a future incompatible notice change safely rejects and needs an explicitly reviewed new proposal rather than silent migration. The chosen proposal consent is retained privately for audit; canonical consent remains in the existing canonical claim.

Only the REAL current customer/session may accept. No auth claim or role is substituted. Successful acceptance creates exactly one actual lost-secret-review claim and calls the existing bridge as that same customer. It verifies the returned own case/pending status against actual case+claim+actor mapping and the exact attachment receipt before reporting accepted or persisting attachment_id. A missing/mismatched witness instead retains a generic review_required receipt without raising and rolling back canonical quota counters. Result: `{request_id,proposal_id,case_id,state:'accepted',claim_id,canonical_status,attached:true,approval_required:true,link_created:false}`. **Accepted means pending review, never approved linking.** Original owner exception evidence must still be checked at final approval. No old contact or phone value acts as proof.

If the original creator records ordinary quota/proof failure, acceptance retains that failed receipt and returns state review_required, attached:false. It must not raise after that ordinary failure and roll back counters. Same nonce replays without another attempt; one proposal accepts at most once. This failed terminal attempt does not create a permanent mapped/accepted-case dead end: a NEW owner-audited proposal can be prepared later, while no old attempt reissues or quota is reset.

`get_my_visit_recovery_acceptance(p_request)` returns the matching own immutable result or absent/closed/manual_review_required with definitive_failure:false except closed. `close_my_visit_recovery_acceptance(p_request)` settles under the same request and canonical request locks: business-won receipt wins; otherwise permanently closes the acceptance nonce. An unrelated direct canonical request with that nonce requires manual review rather than a false failure. Foreign nonce owners are denied. This fences delayed **adapter acceptance**; it does not modify the backwards-compatible original claim API. Explicit UI acknowledgement only clears the local UUID after a known terminal result; it does not delete server audit or undo a claim. Absent alone cannot authorize a new request.

## Lock-order review

| Path | Ordered locks / reads |
|---|---|
| Owner prepare | proposal nonce → actual owner/session share locks → case-proposal mutex → investigation requester identity share locks → case share lock. It takes **no** canonical profile/receipt lock after the case. |
| Owner get/close | proposal nonce → actual owner/session proof → immutable proposal/closure/acceptance reads. Close never calls canonical approval. |
| Customer accept | acceptance nonce → proposal nonce → canonical claim-request mutex → canonical Auth-actor mutex → receipt mutex → profile mutex → existing canonical contact-set SHARE freeze → actual requester session/identity share locks → existing creator → existing attach's fresh attachment nonce/self-owned canonical mutexes → case actor mutex/case update. |
| Acceptance get/close | acceptance nonce → canonical claim-request mutex → actual session; no proposal/profile/case mutation. |
| Existing owner final decision/revoke | Existing owner command/decision nonce → canonical Auth actor/profile → existing contact freeze/Auth rows when approving → bridge case actor/case update. Adapter does not take owner decision nonce. |

Acceptance deliberately never calls the investigation-case/detail helper before canonical locks: that would acquire Auth/case locks in reverse order. It preholds the same contact freeze before real Auth rows as the existing approval/attachment paths, not a new alternative contact authority. At acceptance the frozen contact set, case identity, issuer's actual active owner status, TTL, receipt consumption and active conflicts are rechecked. Final approval independently rechecks them again. Owner proposal close serializes on the exact proposal mutex; customer acceptance close serializes on the exact acceptance plus canonical request mutex. No canonical request is created by a close operation.
