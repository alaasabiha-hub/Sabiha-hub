## Minimum server design

CLI source migration005449 leaves the durable inbox, templates, receipt identities, list/mark RPCs and grants unchanged. Add immutable PRIVATE `app_inbox_hint_targets(event,recipient Auth UUID,recipient kind,server time)` with no client/table grants. These are dispatch INTENTS, never acknowledgments that a recipient received/viewed a message. No new worker, cron, external provider, push, SMS or subscription purchase.

An AFTERINSERT trigger on actual new inbox events selects only its exact customer or current active owner rows with nondeleted/unbanned Auth accounts. Current owner/Auth rows are locked SHARE in sorted order and SKIPLOCKED; accounts undergoing role/ban changes may miss the best-effort hint rather than blocking the case transaction. Only those current targets are appended; no historical/shared-owner broadcast or backfill. Existing exact append retries return before INSERT, producing neither duplicate targets nor duplicate signals.

The target AFTERINSERT trigger calls positional `realtime.send` with exactly payload`{"kind":"inbox_changed"}`, event`inbox_changed`, topic`app-inbox:<recipient Auth UUID>`, private`true`. This is the fixed **application payload**. Root inspected the installed managed send definition (`runtime/realtime-send-installed-definition.sql`): because the application supplies no id, Realtime generates a fresh transport UUID, adds `id` to the payload, and stores the same UUID as `realtime.messages.id`. Therefore the actual managed/wire payload has exactly `kind` and `id`. This ID is transport metadata, not an inbox/case/source/recipient business ID, permission or command nonce; clients must not use it for navigation, matching or authority. The rollback fixture checks exact two-key payload equality against the actual managed row UUID and excludes every inbox/source/case/recipient UUID. The managed function and application call are unchanged. It never uses broadcast_changes/NEW/OLD records, private message content, titles, counts, case/event IDs, names, phone or email. Transport failures do not roll back valid durable case/inbox work. Intent remains; no fake success/delivery flag is written. All successful managed message inserts participate in the caller transaction; rollback removes them. Future actual WebSocket acceptance must verify that no rolled-back hint reaches a client.

One narrow message SELECT policy allows only broadcast +row topic equals requested Realtime topic +actual own actor/session/account check. An additional restrictive authenticated namespace guard protects this prefix from future broad permissive read policies. A restrictive client INSERT rule blocks this prefix; no publish allow policy or direct private-table SELECT grant is added. The private boolean policy helper exposes no data and is not granted to anon/service_role. Realtime RLS is already enabled: do NOT alter managed schema/table RLS ownership, create publications or expose private inbox tables. Source refuses installation atop unexpected existing policies, requiring explicit review.

## Official documentation constraints

* [Broadcast](https://supabase.com/docs/guides/realtime/broadcast): database sends insert managed realtime.messages records; private server/client configurations must match. Its private flag does not itself protect database SELECT access. Database messages are transient; durable private inbox events remain the source of truth.
* [Realtime authorization](https://supabase.com/docs/guides/realtime/authorization): RLS SELECT controls receiving and INSERT controls publishing. Policies are cached during a connection and refreshed at join/new JWT, not per message. Realtime message RLS is already on; attempting to alter managed RLS ownership can fail.
* [Database change subscriptions](https://supabase.com/docs/guides/realtime/subscribing-to-database-changes): recommends Broadcast; raw row-change broadcasting is deliberately not used for private inbox contents.

Important operational caveat: official Broadcast docs describe daily message partitions created by a Realtime client connection; realtime.send may warn/drop when today's partition is absent. Therefore this feature cannot claim guaranteed instant delivery merely from a void function return or an intent row. No paid fallback/plan upgrade is authorized. Use the existing service within its configured limits, with authorized RPC catch-up. Actual local Realtime publication/connection readiness, client/table grants, public-access setting and quota behavior must be verified by root before activation; no assumption of hosted plan/cost was made.

A former owner is excluded from NEW owner-pool fanout. An already-committed generic packet can still be in flight and cached channel authorization cannot revoke it retroactively. It carries no content/authority. Only a fresh existing inbox RPC can show content and that rechecks actual session/current DB role. Do not claim that JWT metadata or channel membership authorizes owner reads.

## Client design only — no Dart changes yet

A single authenticated foreground supervisor per session owns ONE private actor topic using installed Dart RealtimeChannelConfig(private:true). No public/pool channel, client send/presence, raw private-table subscription, local message cache or case IDs in hints.

1. Capture actor/session and initial GoTrue ReplaySubject event; ignore only the matching first replay. Join with current Auth token; after SUBSCRIBED always call existing list_my_app_inbox to establish/catch up authoritative unread state.
2. Validate event `inbox_changed`, exact application kind and only the managed UUID `id` metadata described above; ignore that ID for all business decisions. Never query managed message rows from the client to validate it. Then debounce/coalesce hints into that same authorized RPC refresh. Keep a dirty flag if a hint arrives during a request, so a trailing refresh is not dropped. Hints never create messages, increment counts, mark read, approve cases or navigate by untrusted payload.
3. Show a localized dashboard inbox badge/generic alert only from successful server count/items; preserve the existing explicit mark-read RPC and per-user read state. No historical backlog toast on initial login. Any link/action comes from authorized RPC data and rechecks its own server permission.
4. On account/session/role loss, bump epoch, clear badge/content/queued callbacks and remove only the owned channel. Old replies and broadcast callbacks cannot repopulate another account. Refresh/rejoin with current token after genuine auth refresh; never trust user_metadata. Permission failures clear stale owner content.
5. Use SDK bounded reconnect plus one foreground fallback poll (existing20second cadence is sufficient for missed hints) and immediate refresh on resume/reconnect. No background timers/notification promise. Poll even when connected if desired: silent DB broadcast warnings are otherwise undetectable from channel status. Cancel timers/channel on logout/background/dispose and avoid duplicate supervisors across routes.
