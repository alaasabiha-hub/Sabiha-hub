## What this first stage actually does

* Extends the **same** `private.canonical_loyalty_visits` ledger with `offline_profile_id`, `source_channel` and an exact `offline_order_snapshot_id` FK. Existing `customer_id` and `booking_id` FKs remain, while their NOT NULL requirement becomes conditional: booking rows retain real Auth customer+booking and no offline profile; offline rows would require a real private profile, no Auth customer/booking and the exact source order snapshot. Existing IDs, earn-per-order/reversal indices and immutable history remain. No transfer, copy, synthetic Auth/booking, monetary points or legacy balance import.
* Explicitly rejects **every offline ledger insert**, including privileged/private attempts, with55000. The private runtime is initialized false and a check constraint prevents toggling it true. No activation RPC or test bypass exists. A future reviewed migration must install the complete kernel before any of these fences can change. Existing evaluator/reconciler/outbox/drain/scheduler/cohort/wallet/allocator definitions are not replaced.
* Adds nullable `offline_channel_terms` to the existing immutable `loyalty_policy_versions`, not a parallel policy engine. All old versions and legacy save RPC inserts remain NULL, meaning no guest expansion. Non-null future terms require exact explicit request payload and a strict schema: service_visits, offline_walk_in, order_created_time, explicit enabled boolean and explicit null-global or actual private-profile targets. Auth UUID audiences never match offline profiles by coincidence. Public owner configuration for these terms is deliberately not implemented yet.
* Captures private immutable snapshots on **new live-creator** `offline_walk_in_subjects` only when explicit offline terms exist. Frozen fields include actual profile/car/order/branch/service, canonical policy ID/full snapshot, exact typed channel terms, optional latest activated rule reference/full frozen rule snapshot, and declared eligibility at creation (service, audience, live offer/catalogue kill switch, frozen window). These are **eligibility declarations, not earned credits**. `earning_authorized:false` is immutable; no future activation can make snapshots captured during this disabled stage earn retrospectively. No INSERT SELECT/backfill or old-order scan is included.
* Supplies private typed owner/readiness helpers only, with no new client grants/RPC. Rule references are informational while disabled; they do not bind a spendable credit or adopt a cohort. Private snapshots must never be returned wholesale by a future customer wallet: they can contain targeted audiences and must use the established whitelist/privacy approach.

## Existing paths remain the authority

Actual Walk-in subjects remain `customer_id=NULL,booking_id=NULL` with frozen worker commissions. Completion alone, payment_method text or received work never earns. Existing guarded work transitions and actual full cashier-confirmed settlement will be mandatory when the evaluator adapter is implemented. No new event consumer or parallel scheduler is added; current booking-less events continue to be excluded by the existing enqueue/evaluator path. No old invoice/commission snapshot is revised.

Reviewed app links remain access evidence only. The offline profile will own its own future credits even if a customer reads them through a live reviewed link. No row reassigns credit ownership to `auth.uid()`. Existing history consent explicitly excludes rewards; registration consent and known phone/receipt do not grant wallet or spend authority. The existing full Auth-booking reward and refund paths retain their original ledger/cohort functions. New guard additionally refuses mismatched owner/source on a newly inserted booking reversal; valid reconciler-generated reversals keep the same values and path.

## Why activation must remain impossible in this stage

Required follow-ups, not claimed implemented:

1. Owner-only explicit new policy/channel/typed-audience configuration and channel activation with an actual future cutoff, independently consented reward scope and tested gates. No old booking activation implicitly authorizes guests.
2. Extend the **one** shared evaluator/reconciler/outbox to validated completed typed work+actual trusted settlement and exact matching refund reversal; preserve order mutexes, deterministic invoice locking, retry/backoff and20s bounds. Test both commit orders and actual refund-before/after-drain; no new scheduler.
3. Typed ownership in the existing reward claims/quotes/redemptions/refund-review/debt kernel and all callers, one owner-lock vocabulary, frozen original cohort/expiry and newer-rule ordering. Existing Auth routines must not become a separate spend path alongside guest routines. Current foundation inserts no credits until that consistency is proven.
4. Live link/session/contact reauthorization plus independent wallet-read/spend consent, separate unsummed owner/program pools, owner conflict handling, quote-specific customer assent and durable close/retry/recovery. No phone-only spending or cached-link access.
5. Complete typed reward issuer/zero-due coverage, cancellation restore/forfeit, consumed-contribution refund offset/freeze, and explicit actual worker commission recognition for reward services without fake cash sales. Existing financial guards continue to reject unsupported offline reward issuance.
6. Focused SQL/HTTP/concurrency/browser acceptance and owner readiness/capability UI before any supported flag can become true. Generic monetary points are a separate unimplemented unit and remain out of scope.
