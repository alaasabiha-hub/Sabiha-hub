## Records and contracts

Three new immutable private RLS tables hold proposal, customer consent and revocation audits. No client has table access. There is no public owner proposer or arbitrary customer/profile parameter.

The ungranted private `propose_offline_reward_financial_consent(proposal UUID, preparation UUID)` requires the original current owner/operator of an actual accepted-22019 preparation. The server finds its actual live approved profile link. It rechecks exact current held quote/allocation/expiry/refunds/benefit facts and freezes the entire private witness, linked customer/link IDs, supported four rules and a minimal public display. Its opaque SHA-256 fingerprint binds all of that. One proposal exists per preparation. Owner replay retains the original proposal without claiming it remains current.

Authenticated public invoker wrappers:

* `get_my_offline_reward_financial_proposal(p_proposal UUID DEFAULT NULL)`: actual customer's exact own proposal; null discovers the latest proposal for the caller's current actual link. Foreign/unknown UUID returns `unavailable`, never profile/contact/credit data. Valid response `state=proposal` has `proposal_id`, `fingerprint`, minimal `terms`, separate `consent` notice, and issuer/redemption/reward-issued false. Expired/refunded/released/closed/changed hold returns `inactive`. This is the backend discovery seam; no app/inbox UI is wired by this stage.
* `accept_my_offline_reward_financial_consent(p_request UUID,p_proposal UUID,p_fingerprint TEXT,p_consent JSONB)`: exact consent keys `accepted:true`, `version:offline-reward-financial-v1`, `language:ar|en`, `text:<exact returned financial notice>`. A stable nonce replays only the same proposal/fingerprint/consent for the same actor/link. A changed payload is rejected. Only one immutable consent nonce is permitted per proposal; withdrawal cannot revive it.
* `get_my_offline_reward_financial_consent(p_request UUID)`: exact own restart receipt with retained exact assent and own proposal. `absent` is nondefinitive, `consent_recorded` remains future-only, `inactive` means facts no longer support use, `revoked` is definitive for that nonce. Current identity/session/link is rechecked before cached results. No PII is required in local recovery storage; only nonce/proposal UUIDs.
* `revoke_my_offline_reward_financial_consent(p_request UUID,p_consent_request UUID)`: immutable exact revocation request. It also fences an unknown acceptance nonce to block a delayed producer. Changed revocation request payload is rejected; separate revocation nonces on the same target each retain their own audit. No accepted row, invoice, payment or hold is deleted/rewritten/released.

The display contains only current frozen service/branch names, service-visit count, currency EGP, gross amount, reward discount equal to gross, amount due zero, exact four frozen rules and proposal expiry. It contains no contact/email/profile/car/earning/order/history IDs. Full original allocation/expiry/cohort/car/subject/rule evidence is private and fingerprint-bound. AR/EN financial notice explicitly names this service, number of visits, gross/discount/final-zero price and expiry, and states no automatic reward issuance or credit transfer.
