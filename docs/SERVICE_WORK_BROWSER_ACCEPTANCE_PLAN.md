# Shared service-work browser acceptance — prepared source only

`tools/service_work_browser.py` does not run without `--execute`. The coordinating agent owns fixture preparation, scheduling, actual execution and cleanup. This source phase performed no browser, DB, build, operational or financial actions.

Require the completed `service-work-integrated-web-build-source.json`: successful loopback build, every Dart/dependency source hash unchanged, served compiled JS exactly matching the manifest. The build uses local renderer resources. Static HTTPS font GETs are allowed only for `fonts.gstatic.com/s/*.woff2`; remote APIs/Auth/Storage and all other external traffic are blocked.

Root supplies ONE fresh tagged received typed Walk-in order. With `--entry-mode service_card`, it may be on a NONdefault isolated QA branch: navigate to actual Staff operations and click only its exact fresh service-order ListTile. This mode forbids the queue RPC and does not assert/default/rewrite the branch. With default `--entry-mode queue`, require the actual default branch because that AppBar entry intentionally chooses it. Never flip the default branch or branch hours to bypass a closed branch. Fixture JSON must contain `local_only:true`, `root_approved:true`, `fresh_qa:true`, `source_kind:"walk_in"`, `initial_status:"received"`, actual `order_id`, `branch_id`, `service_id`, `invoice_id`, `service_name`, `gross_amount`, `tag`, `actor_role` (`manager` or `owner`), and ordered `allowed_transitions`. The tag must be present in the actual service name. Preflight joins the actual private subject/order/catalogue bindings, verifies no Auth customer/booking fabrication, received state, no prior physical span and no other own prepared/unacknowledged operational command. Root must provide evidence of fixture freshness and retain its cleanup plan; a JSON approval flag is a local test instruction, not a production authorization mechanism.

Default execution is READ-ONLY route acceptance: actual staff login and verified user match, Reports → Manage bookings & assigned work → either exact known fresh service-order card (`service_card`) or actual Service queue AppBar and exact known work-reference row (`queue`) → actual `get_service_work_context`. Validate branch/order/source/service against the provided fixture and capture a settled real AR390 or EN1440 screenshot. No arbitrary order is clicked. No static header is used as a navigation anchor.

Only `--transitions` enables operational mutations. Each exact next status must be both explicitly present in the root fixture and the authoritative current context. Explicit reason entry → prepare exact order/old/new/reason → actual saved command. On the first prepared step, reload and return through the real queue; require exact stored UUID and identical server payload before continuing. Apply once → validate actual same-order performed status → settled screenshot → explicit UI acknowledgement → server acknowledged result and local UUID cleared. Continue only the next permitted action. No direct order/booking table writes or private action fallback exists.

A browser route guard checks exact mutation key sets, provided order, expected status, next status, reason and immutable nonce. It records the command UUID and exact preparation in a private local state file BEFORE allowing dispatch. Place/ack are restricted to that recorded nonce. Close is deliberately not automatically invoked. Failure preserves the pending nonce/state for root to recover/close/ack as the actual creator; never mint a replacement based on absence or silently repeat a completed transition. Each successful transition is checkpointed independently. A later failed check does not invalidate or authorize repeating earlier physical work.

No finance, invoice creation, refund, payment, loyalty/reward, registration/claim, provider, Auth-account creation, fixture creation or automatic cleanup RPC is permitted. Before/after hashes verify invoice/payment/canonical-credit/claim/redemption/employment rows, document counters and Auth user identity remain unchanged. Operational order state, physical spans, command/ledger receipts and generated reconciliation jobs are expected to change only for the approved real operational flow; this harness never drains jobs or grants visits. Root verifies other business-row preservation and physical-span/ledger deltas alongside its fixture journal. An unpaid Walk-in must not earn loyalty from completion alone.

Run each locale independently and preserve partial proofs; do not repeat accepted Arabic invoice production or the existing intake/handoff journeys. This harness cannot provide those proofs and makes no QR, settlement, loyalty, ETA or tax-compliance claims. Real resource/inspection/branch-hour blockers remain authoritative; stop rather than change configuration or bypass them.
