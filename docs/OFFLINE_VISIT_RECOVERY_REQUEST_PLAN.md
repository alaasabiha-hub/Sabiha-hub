## Smallest request lifecycle without a parallel link engine

Add a private **case envelope**, e.g. `private.offline_visit_recovery_cases`, plus append-only case events and exact request receipts. Names below are proposed, not existing APIs. Fields: case UUID, claimant Auth UUID, version, status, bounded submitted hints, consent version, created/updated time, optional existing claim UUID and owner-selected proposal version. Store no raw enrollment secret, password, customer email entered by staff, document scans or wallet values. Existing immutable proof/link/financial tables stay authoritative and unchanged.

Open statuses: `submitted`, `under_review`, `awaiting_customer_evidence`, `claim_pending`. Terminal: `resolved`, `rejected`, `withdrawn`, `expired`. `resolved` means the canonical review command succeeded; actual usable history still depends on current live reader checks and scope consent. Revocation changes current access immediately and may emit a case event; do not rewrite immutable old decision receipts or pretend an old resolved receipt authorizes access forever.

Proposed wrappers:

* `submit_visit_recovery_request(p_request,p_details,p_consent)` requires the actual live confirmed customer account/session. Fixed bilingual purpose consent, exact allowed keys/lengths; optional known receipt reference, approximate visit date/branch and bounded explanation. Phone/name/plate hints are investigation data only. Customer must not submit a target profile/Auth UUID. No customer-facing search/existence counts. Stable UUID exact replay returns the original case; same UUID changed payload rejects. Under a per-actor mutex, one open case per claimant (unique partial index); a new nonce while one exists returns its safe reference/state, never creates another open case or silently replaces its details. Explicit customer amendment with expected version is the only way to change submitted facts. Rate-limit only genuinely new cases/amendments; do not reset existing claim budgets.
* `get_my_visit_recovery_request(p_case default null)` derives caller ownership; null discovers the caller's open/unacknowledged case. Return safe state, own submitted hints, evidence tasks, timestamps and canonical claim status. Unknown/foreign UUID has uniform unavailable. No candidate list, profile contacts, old visit counts, balances or invoice tokens until authorized history readers allow them.
* `list_visit_recovery_requests(p_status,p_before,p_limit)` / `get_visit_recovery_request_for_review(p_case)` are active-owner-only, bounded/paginated. Owners see the submitted evidence and proof flags needed for investigation; managers/cashiers cannot approve or enumerate cases. Current role is rechecked server-side, never JWT user metadata.
* `update_visit_recovery_case(p_request,p_case,p_expected_version,p_action,p_details)` performs only investigation status/evidence requests/rejection/withdrawal or explicit customer-owned amendments. Action/actor allowlist and expected-version check; durable exact command receipt and permanent close semantics for uncertain owner mutations. Reuse the171803 architecture; do not claim an absent lookup fences a delayed HTTP command. Only a known terminal result/authoritative close permits a new action UUID after uncertainty.

Known-receipt positive/lost-secret requests reuse `request_offline_customer_claim`, then associate that immutable claim with the case under the caller/account check. The case cannot promote a generic failure into proof. Existing claim limits, consumed-receipt uniqueness and exact payload remain intact. A post-approval case event must not consume another claim attempt.

For a request with **no usable receipt**, keep it an investigation case, not a synthetic canonical claim. Owner-only bounded candidate lookup may use permitted observed contact/plate/service clues after explicit investigation action; log query purpose/hash rather than full search text, minimize returned fields and never expose lookup to customers. Candidate match is not identity proof. The owner verifies independent in-person continuity, then can propose an actual existing receipt reference to the customer using an immutable proposal version/contact digest. Customer explicitly confirms that selected receipt and current identity-review consent, then the normal lost-secret claim API runs as that customer and the existing owner `approve_exception` path remains mandatory. This customer confirmation is necessary to bind consent to the selected historical identity; it is not a second link/approval engine. The same active owner may investigate and make the existing final approval. Never manufacture a secret/receipt for a legacy profile or transfer a consumed/revoked receipt. Profiles without canonical enrollment evidence remain manual unresolved until a separately reviewed evidence-enrollment adapter exists.

Owner hold/reject must remain possible without disclosing candidates. If account email/contact evidence changes, suspend the canonical claim and request fresh evidence; no silent reassignment. Shared/recycled phone, stolen receipt, competing existing links or account deletion remain explicit review/conflict cases. Do not merge UUIDs, rewrite FKs, relabel cars as legally owned, backfill credits or issue fake rewards.

## Atomic bilingual in-app events

Add one small generic private transactional inbox foundation, e.g. `private.app_inbox_events` + `private.app_inbox_reads`. It transports case events; it never grants access. Event fields: immutable event UUID, source_kind=`visit_recovery`, source case UUID, source event/version, recipient scope (`customer` with exact Auth UUID, or `active_owner_pool`), template code/version, minimal whitelisted parameters, bilingual title/body snapshots, created_at. Unique source event + recipient scope/identity prevents duplicates. Owner-pool rows are readable only by **currently active owners**; do not materialize permanent privileged access for departed staff. Read-state uses(event_id,user_id) uniqueness and monotonic read_at, never alters source events.

Create the case/state transition, audit receipt and all notifications in the **same DB transaction**. Submission produces owner-pool `recovery_submitted` and own-customer `recovery_received`; investigation evidence request, canonical approval/rejection/hold, withdrawal and revocation produce their appropriate fixed templates. Replayed business/owner UUIDs insert nothing new. If inbox insertion fails, business transition rolls back; no approved claim without its promised committed in-app notice. Add narrow internal hooks to the existing canonical decide/revoke functions so **every** reachable writer (including legacy direct RPCs and prepared commands) emits once. Never rely only on Flutter or a sidecar case wrapper that direct canonical RPC calls bypass. Do not modify historical decisions or retrospectively send guessed notifications.

Templates must distinguish identity review from access: “Your identity review was approved. Open linked reception history to check available records” / «تمت الموافقة على مراجعة الهوية. افتح سجل الاستقبال المرتبط للتحقق من السجلات المتاحة». No guarantee of wallet/rewards/history if the reader gate is disabled, consent missing or proof stale. Rejection/evidence-request messages use safe customer-facing reason codes, not private owner notes or allegations. Links navigate by **own case UUID**, then reauthorize via current case/claim/history RPC; no direct profile/invoice/secret/token in inbox payload. Changing locale selects the stored Arabic/English template; no external AI call.

Proposed `list_my_app_inbox(p_before,p_limit)` and `mark_my_app_inbox_read(p_request,p_event)` are authenticated invoker wrappers over explicitly authorized private functions; max page bound, no supplied recipient UUID. Read acknowledgement is idempotent and cannot suppress another user's owner-pool unread state. Resolve current source access on each open, so old notification cannot reopen revoked history. Customer notifications reveal only own case; owner recipient/source content is owner-only. Keep raw table clients revoked/RLS enabled; service-role metadata is not a customer authorization shortcut.

Reuse the current customer bell/inbox host with an additional typed case section while preserving existing order notices and their real(order,status) keys. Do not duplicate prior order events or migrate/destroy their push state. Root owns main/owner navigation. Push is optional later: in-app read/creation must work without FCM, SMS, email, paid services or marketing consent. Existing transactional push preferences/tokens can be reused only after explicit notification-scope review; failed external delivery never duplicates the in-app event or changes review outcome.

## Concurrency, privacy and acceptance before enabling

Use a documented fixed mutex order compatible with existing claim-request/actor/receipt/profile and owner-global-command locks, READ COMMITTED and bounded waits. Case submission and canonical request must not invert those locks. Insert-only events/read receipts are separate from immutable proof; contact updates and revoke still use current canonical authority. A case cannot reactivate an already revoked link. Scope consent remains185540; case consent is not a substitute.

Required isolated SQL/HTTP/two-session proofs: same/new nonce simultaneous submissions give one open case; changed replay rejects; authoritative close versus delayed owner action both commit orders; strict customer/owner/cashier/other-account isolation; unknown receipt/candidate nonenumeration; live session/email/contact change; already-consumed/conflicting links; expired claim; exact one canonical link/claim with unchanged legacy IDs; notification failure atomic rollback; all direct/prepared canonical approval/revoke paths emit once; hold/reject/revoke templates and owner read receipts independent; cursor bounds/unread counts; no private owner note/secret/contact/balance leakage; no finance/loyalty/customer/vehicle rewrites. Use legitimate quotas, no resets/new Auth users.

AR390/EN1440 actual Flutter acceptance then checks submit/open/recover own case, owner review/evidence gate, customer notification and locale, reload/unknown-response safety, one-event idempotency, read acknowledgement, canonical approval/revoke and immediate protected-history reauthorization. Preserve all prior row hashes/counters except explicitly approved new case/event/read/audit facts. Current accepted claims and history proofs are reused, not repeated wholesale. No feature is complete merely because an inbox card exists.
