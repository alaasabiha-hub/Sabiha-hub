Status: read-only dependency plan, 14 November 2026. No migration, engine change, database write or new activation is authorized by this document. The accepted offline intake and reviewed claim evidence stages do not yet grant old history, wallet or rewards access.

## First complete, testable slice: a paid walk-in without loyalty

Implement actual reception, service work and cash collection for **both** subject types. Do not claim earning, points, redemption or historical visibility during this slice.

Proposed additive private tables:

1. `walk_in_service_requests`: actor/request UUID, exact canonical payload, result/order reference, creation timestamp and immutable audit. Global request mutex before actor lookup; changed actor/payload fails. Durable recovery returns only the initiating authorized staff member's own receipt. No plaintext enrollment secret is copied into it.
2. `walk_in_service_subjects`: one immutable row per existing service order, with `subject_kind='auth_customer'|'offline_profile'`, exactly one real customer/profile FK and corresponding vehicle/car-ref FK, actual branch/service, reception consent, price/name/car snapshots and source `'walk_in'`. Cross-check subject/car ownership, order branch and the nullable order customer. `booking_id` stays NULL. An offline order has `customer_id=NULL`; its profile ID never enters that column.
3. `walk_in_reception_entries` plus exact command/audit receipts: keyed by order ID, arrival, normal/VIP priority, revision and operator. Union with the existing booking queue using typed `(source_kind,source_id)` references. Employee view remains assigned-work only; owner/branch manager changes priority with a reason. In-service first, then arrived VIP/FIFO across both types; use actual arrival timestamp, never a fabricated appointment slot.

Proposed public invoker/private definer RPCs (names provisional until source contract approval):

- `create_walk_in_service(p_request,p_branch,p_service,p_subject,p_car,p_expected_price,p_consent,p_notes)` validates active authorized reception/cashier role from DB, branch availability and catalogue service/price. It creates subject/order/item/reception/invoice atomically, returns short order/invoice references and capabilities false. No arbitrary client total, discount, payment status, commission or reward flag is accepted.
- `get_walk_in_service_request(p_request)` returns only own canonical outcome; absent is explicitly nondefinitive because a delayed create may still commit. Stable UUID-only local recovery plus a server-prepared exact payload/tombstone stage is required before calling create from a restart-safe UI; do not repeat the earlier shop retry race.
- Typed reception update/read RPCs operate on actual order UUIDs. Work progression may reuse current guarded order status updates only after branch/assignment tests demonstrate it; a narrow explicit transition RPC is preferable if cancellation/invoice coordination is required.
- Cash sale/refund reuses `record_shift_payment` with the real invoice and an open authorized shift. Completion is not payment. Creating an invoice is not payment. Never add a second cash ledger.

Auth subject selection is an intake association, not phone authority. For an app customer, a minimal account-authenticated, branch/car-bound one-time reception authorization can be presented to staff and consumed atomically; it authorizes this **new service** only. Without it, a phone match must not let staff silently attach service/history to an arbitrary Auth account: use an observed offline intake or owner-assisted review. The exact UX needs root review before a contract is frozen. An offline profile/car reference must be valid for the authorized intake branch and known intake receipt; it does not expose balance or other-branch history.

Restrict the first slice to existing positive-price standard service items. Preserve any specialist-service exclusions unless an existing explicitly authorized management route covers them. No arbitrary zero-price, reward, coupon or invented address/fee handling. Capture only actual configured invoice/payment/commission facts. Reception capacity/resource restrictions must be explicitly reused where applicable; do not create a fake future booking to pass slot triggers. If simultaneous bay/work capacity is not currently modeled independently of bookings, keep intake queued and require the existing authorized assignment/start-work control rather than implying a reserved bay.

New walk-in source exclusion in `finalize_service_loyalty` is part of this slice: preserve legacy replay first, then return false/unchanged legacy balance for any typed walk-in order before unmanaged-offer selection. Offline orders cannot legitimately call the customer-bound legacy routine at all. Do not globally disable legacy behavior for unrelated historical orders.

Unpaid cancellation atomically marks this order cancelled and its active unpaid invoice void, retaining all rows and original document. Paid/refunded/uncertain-gateway cases require existing management/refund workflow; no cancellation side effect invents a refund. Follow payment lock ordering: payment owns shift → invoice; service commands must never acquire a shift after invoice/order locks. Test actual concurrent collection/cancel/start operations, not just sequential RPC calls.

## Next dependency: one canonical typed earning/credit path

Do not copy the booking visit evaluator into a separately maintained guest loyalty engine. The source adapter must share validation, immutable earning facts, refund reconciliation, allocation occupancy and replay keys with the existing engine.

A safe future design needs a typed service-source registry and normalized credit interface that can address immutable booking lots and new walk-in lots without rewriting old rows. Namespaced lot/source references must make `booking:<earning UUID>` and `walk_in:<earning UUID>` unambiguous. Booking rows remain in the existing canonical table; new walk-in facts can live in an additive typed extension only if the **same** worker/reconciler and allocator enforce both. Table separation must not mean independent balances or competing spend decisions.

This is a concrete dependency rather than a promised implementation: existing `reward_credit_claims.earning_id`, refund reviews, quote earning UUID arrays and helpers are hard FKs to the booking-only canonical table. A UNION view alone cannot make guest credits spendable or prevent double spend. Root must approve and test a single shared occupancy registry keyed by immutable source-lot identity, with transactionally compatible adapters for existing booking claims, before enabling either-channel pooling. It must count existing active claims and refund-offset claims, never import legacy points. Existing booking allocation continues unchanged until the unified adapter is proven; there must be no interval where a lot is spendable through two allocators.

An alternative is a carefully constrained evolution of the current ledger to typed subject/source columns while retaining every existing FK/UUID/row, with booking/customer NOT NULL rules replaced by validated per-kind checks. That is **not** a purely additive migration and would require explicit review of every current join/claim/refund function and rollback limitations. It must not be hidden in the first walk-in slice. Prefer the additive typed registry/adapter design, subject to this cross-channel concurrency proof.

At walk-in creation, an actual explicitly activated owner policy must freeze service eligibility, threshold, reward service, expiry, pooling, cancellation and refunded-contribution terms for that typed source. Current booking policy uses `eligibility_basis='booking_created_time'`; do not silently relabel it as walk-in intake time. Owner-saved/activated supported terms must explicitly permit the walk-in channel and subject type. Existing targeted-customer UUID lists cannot implicitly target an offline profile. Without these terms, `walk_in_loyalty_accrual=false` remains accurate.

A qualifying new visit needs actual completed service/order, one authoritative active invoice, trusted full settlement in the actual branch, no refund and a frozen policy captured after explicit activation. Retries/outbox workers must award once per source order, reverse once per actual refund and converge even when refund races earning. Electronic/sandbox records are not trusted cash. Reward-covered zero-due service is not a paid qualifying visit unless future explicit owner policy supports that precise case.

Current canonical unit is `service_visits`. User-requested points need their own explicit owner-configured unit, earn/cap/expiry and redemption terms; neither legacy balances nor money may be converted by assumption. A unit enum or copied legacy points table does not implement a points program.

## Trusted-link readers and walk-in redemption

An approved private claim is evidence, not an existing public customer FK rewrite. Retain offline profile and Auth customer UUIDs and each source's original subject forever. A narrowly scoped resolver may return both identities only when current actual Auth email/contact bindings and nonrevoked owner approval are valid. Linking must not copy offline visits to the Auth ledger or reassign invoice/order customers.

Before exposure, audit and adapt each intended path independently: typed order history; actual service/car history; invoice lists; `can_read_invoice`; invoice/QR/PDF and print queue; private photo storage and inspection reads; reviews; exports; wallet/quote/allocation; notifications; branch staff tooling; owner analytics/AI scopes. Direct Flutter table equality filters do not become linked-history readers merely because one RPC was changed. Cross-customer/branch/revoked/stale-link tests are mandatory. Leave unadapted surfaces denied and all global readiness flags false.

Future redemption requires transaction-specific customer approval independent of the observing cashier. Auth customers can consent through their actual authenticated account. An offline customer without Auth needs an independently approved supported proof/consent procedure; phone/name/plate alone or a cashier-visible enrollment secret is insufficient. The accepted owner-review link does not implement a no-Auth transaction approval method. Until a trustworthy procedure and shared allocator are implemented, no-Auth redemption stays disabled rather than pretending the walk-in enum authorizes it.

Canonical reward coverage must exist before final zero-due invoice INSERT, with actual allocation/consent/cover-event witness; use truthful `covered_by_reward`, preserve gross/discount/commission base and mint no sale event. Current booking-only coverage helper/creator needs a typed walk-in adapter and actual creation-snapshot tests before enabling this path. Cancellation restores original-expiry lots or forfeits only according to their frozen rule; qualifying-source refunds follow the same shared offset/owner-review rules, never retrospective cash/invoice rewriting.

## Verification and rollout

First slice rollback SQL: Auth and offline service creation produce no bookings/Auth/users/vehicle inserts; exact request replay and changed-payload/actor rejection; valid/invalid branch/service/price/car/subject; no customer phone-enumeration leakage; document snapshot/short numbers/QR; before-discount commission; assigned-worker and manager/cashier scopes; actual work states; unpaid void versus paid management restriction; unchanged old rows/legacy replay; no canonical or legacy earning despite completed cash service.

Local actual HTTP/concurrency: durable request lost response/restart/replay/tombstone races; same nonce two actors; duplicate simultaneous intake; invoice sale/cancel race using real shift lock order; one sale/refund; queue arrival/VIP revision conflicts across booking and walk-in. Retain tagged QA/audit only, revoke QA identity links and close QA shift through actual workflow, no deletions or invented cash reconciliation. Test narrow AR390/EN1440 UI and actual invoice PDFs/QR after source behavior passes; no new broad build for a design plan.

Later shared worker/allocation: outbox retry/deadletter recovery, sale/refund races, source completion after payment, original policy expiry, both channels competing for the same lot, linked/unlinked overlap, offset-credit refund race, rule changes, zero-due creation snapshot, transaction consent and revoked/stale identity. Prove one spend across every allocator and no historic/legacy conversion before readiness turns true.

Each stage gets a CLI-generated follow-up, private RLS/revoked direct grants, definer/invoker boundaries, exact idempotency receipts and audit. Operational rollback disables only new entry points/capabilities and retains financial/identity history; applied tables with real events must not be dropped or rows deleted. Additive storage does not make destructive down-migration safe. Re-enable existing app paths independently; no global reset or financial backfill.

Root approval needed next: first paid-walk-in contract and Auth intake authorization UX. Typed earning/points, link readers and no-Auth redemption are subsequent explicitly tested stages, not acceptance claims for the first slice.
