Source only. CLI-created migration `20261114222258_private_in_app_inbox_foundation.sql` and rollback fixture `supabase/tests/private_in_app_inbox.sql` have NOT been applied or executed. This independent transport slice does not implement recovery cases, identity approval hooks, a Flutter inbox, push delivery or the full recovery journey.

The existing `customer_order_notifications` requires an actual order FK and retains its order/status uniqueness and existing push state. It is unchanged. New tables `private.app_inbox_events`, `app_inbox_reads` and `app_inbox_read_requests` have RLS and no client/service-role table grants. Events and read identities are append-only. There are no seeded notifications or public event creators.

The internal-only `private.append_visit_recovery_inbox(p_source_event,p_case,p_recipient_kind,p_customer,p_template)` is revoked from public/anon/authenticated/service_role. A future guarded same-transaction case/canonical hook can invoke it as the database function owner. It accepts only an opaque future case reference and exact recipient (real customer FK or active owner pool), never a JSON payload, phone, profile ID, secret, amount, invoice token or free text. Source-event plus recipient is idempotent; changed fields under the same identity reject. The case table/hook is deliberately absent, so the opaque reference is NOT authorization and no claim/link can be created here.

Eight fixed version1 bilingual templates cover submitted, received, more information, hold, approved, rejected, withdrawn and access ended. Before-insert validation enforces exact copies and an empty parameter map. Approval wording says identity review was approved and current verification/history scope are still required; no guaranteed history, credits or financial rights are promised.
