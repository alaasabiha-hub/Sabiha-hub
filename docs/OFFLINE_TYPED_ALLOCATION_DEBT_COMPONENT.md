## Why nullable-column-only allocation is unsafe

All of `service_reward_quotes`, `service_reward_redemptions`, `reward_credit_claims` and `reward_refund_reviews` still require Auth customer IDs. Quote additionally requires public vehicle/date/time. A walk_in enum does not make these typed. The current claim check `e.customer_id<>new.customer_id` is NULL for guest credits; the applied offline claim-block trigger must remain until EVERY caller/guard is migrated. Passing an offline UUID into `sync_customer_rewards` selects the wrong owner and lock namespace; passing NULL can omit both locks and rows. Empty debt is not proof of no obligation. The new candidate helpers therefore do not weaken any of those constraints or remove the fence.

The coherent next migration must extend the SAME tables with offline-profile FK plus explicit owner discriminator and conditional old Auth requirements, preserve existing FKs/old row values and global one-active-claim-per-earning uniqueness, and atomically refresh all affected guards, quote/place/recovery/sync readers. Cross-row equality is `(kind,id)` with explicit nonnull checks / IS DISTINCT FROM, never coalescing namespaces. Actor/approver Auth identity is separate from credit owner. No linking operation updates a credit owner.

Redemption's current unique(customer_id,request_id) is insufficient once customer_id can be NULL: add a real typed-owner/request uniqueness constraint for offline rows while preserving old Auth semantics and global nonce fences. Quotes retain a stable PK; new payloads/fingerprints include typed owner/channel/purpose/consent without changing any old quote hash. Whole-row public quote serialization (`customer_reward_quote` currently sanitizes a composite) must receive a fixed old response projection before new private owner columns are added, so new fields cannot leak or break old replay shape. Immutable guard comparisons must protect added ownership fields; no old snapshot/result/hash is rewritten.

## One shared mutation kernel, both owner types

Generalize the existing sync/claim/debt/cancel engine, not two independently spending implementations. Keep existing Auth key `reward-customer:<id>` while migrating wrappers together; all offline callers must use one distinct consistent key, e.g. reward-offline-profile:<id>. UUID collisions across kinds must remain different owners. Acquire financial request/identity proof/owner mutexes then deterministic invoice/claim locks in a documented order. Never acquire a cash shift lock after invoice; existing cashier shift→invoice writers enqueue only and do not call the owner debt sync while holding financial locks.

Before reservation/quote placement, synchronize actual cancellation and full refunded contributions, lock/re-read every proposed lot and already allocated offset credit, and recheck expiry/cohort/claim occupancy after waits under READ COMMITTED. Candidate snapshots alone are not safe to spend. Maintain exact one active occupancy per earning. Cancellation restore releases claims/debt offsets under its frozen choice but never extends original expiry; forfeit retains occupancy. Offset_future_visits applies only to the same typed owner+offer+branch and actual later valid credits, including cross-policy pools only where explicitly allowed. Freeze_for_owner_review blocks new claims until current owner acknowledgment under the same kernel; acknowledgment never waives debt or retroactively charges/voids an issued reward. Refund of an already used offset credit must reopen obligation using actual refund facts. Replayed requests/events append no duplicate claim/review/offset/reversal.

Cohorts have TWO immutable orderings for offline: independent overlay version and original rules version. Older lenient selection cannot use newer credits; a newer explicitly consented selection may use older credits only under the chosen same-offer/branch pool and original expiry. No Auth latest-activation rule is inherited for offline adoption. Current offline credits are bound at creation; unsupported/missing binding stays unavailable rather than inventing rights or converting old visits/points. Mutating offers/new policy/capture pause cannot reinterpret an already earned cohort.

## Financial consent, issuance and remaining boundaries

Linked customer must have current actual Auth/session/confirmed email/live owner-approved link/contact proof plus separate wallet READ consent and quote-specific SPEND assent. Scope is actual offline owner/program/rules/service/gross/benefit/deadline/allocation/purpose; a history scope, cashier possession of receipt, old code, phone match or old cached quote is insufficient. Revocation blocks new quote/place/recovery data access without transferring or erasing credits. A permanently closed attempt fences delayed requests before the UI unlocks.

Unlinked guest requires independently owner-authorized in-person continuity/customer assent under explicit policy; approver Auth UUID must differ from operating cashier (a second session is not independence). Current-owner administrative reading is not permission to spend another person's rights. No public guest spend API exists yet.

Reward coverage is PRE-INVOICE only: do not alter a previously issued positive Walk-in invoice to zero. The same canonical issuer must create new real order/typed source/consent/allocated claims/coverage in one transaction before invoice stamping, with deferred associations where needed. Invoice total+discount equals frozen gross; existing actual worker N/rate/gross/rounded commission lines remain BEFORE benefit. A zero invoice is not a cash sale and must not recursively earn visits. Explicit reward-worker commission recognition/payroll and supported settlement timing remain prerequisites; no invented salary/rate/fee/tax or fake payment event.
