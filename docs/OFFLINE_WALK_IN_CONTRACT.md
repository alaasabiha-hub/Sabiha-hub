# Offline walk-in first slice — proposed source contract

Status: first received-only financial migration and rollback fixture authored SOURCE ONLY, pending root review; no DB application. Existing Auth customer association, loyalty earning, points, redemption and linked historical readers are explicitly unsupported. No Auth user, public customer, public vehicle or booking is created.

## Financial dependencies verified

The existing service catalogue supplies `price`, `vehicle_type`, `duration_minutes` (5–480), `resource_key` and branch. Positive configured service price is the only due amount in this slice; no client totals/discounts/taxes/fees. Published specialist exclusions in the existing booking creator remain unless the existing management route explicitly supports them. Active branch, configured Cairo hours/exception and closure checks must be actual server checks.

Invoice `commission_total` and `commission_share` are NOT NULL legacy scalar snapshots; `workers` is JSON. Canonical HR calculates each assigned worker's commission from `(invoice.total+invoice.discount)*hr_employment.commission_percent/100/assigned_count`, rounded per worker. A caller-supplied rate, a hardcoded common rate, missing employment or unassigned default zero cannot be presented as configured commission. The authorized strategy is a typed per-worker adapter, including heterogeneous rates. Add invoice discriminant `commission_model` (`legacy_scalar` default / `walk_in_frozen_workers`) and immutable private per-worker lines with invoice/staff, actual percent, assigned count, gross, rounded amount and actual employment version/snapshot. Sum the rounded amounts into `commission_total`. `commission_share` remains actual equal amount only for uniform rates; heterogeneous rates require NULL, never average/zero. Relax its NOT NULL only with a guarded typed sidecar proof; old rows/discriminants stay unchanged. The typed creator inserts immutable subject/commission sidecars before final invoice INSERT using deferred invoice FK, so creation guards see full proof. Freeze this invoice's assignment and financial facts at creation. Payroll uses each frozen walk-in line, preserving the old booking calculation unchanged; later employment rate edits cannot change this walk-in commission. Website compatibility must be patched by root before applying nullable typed shares; no blanket null-to-zero conversion.

Invoice snapshot truthfully reports `tax_amount:null` and `tax_configuration:not_recorded_in_legacy_invoice`; this slice must not silently invent Egypt tax zero or a legal tax rate. Shared invoice display numbering, branch, policy, immutable document/QR triggers and cash-shift ledger remain authoritative. No new financial backfill.

## Typed subject and durable command

Private immutable `offline_walk_in_subjects`: `order_id` real order FK/PK, `profile_id` offline profile FK, `car_ref_id` offline car FK, `registration_request_id` immutable intake receipt FK, branch/service FK, original intake consent reference/hash, actual service price/duration/resource and customer/car snapshots. Subject kind is exactly `offline_profile`. Required intake result is created/reused unverified, belongs to authorized same branch and contains those exact profile/car references. Observed phone alone cannot select a profile. No enrollment secret is returned/copied or requested again.

Private `offline_walk_in_commands`: stable request UUID/actor, exact canonical submitted payload, state `prepared|succeeded|closed`, immutable preparation, actual result/order FK and final timestamps. Transition audit is append-only. Server request mutex serializes prepare/create/close, ensuring a close committed first permanently fences delayed create; committed success always replays the actual same order. No rows deleted. No client raw table access.

Proposed invoker/definer RPCs:

- `prepare_offline_walk_in(p_request uuid,p_registration uuid,p_service uuid,p_expected_price numeric,p_cashier uuid,p_staff_ids uuid[],p_notes text)` validates and saves exact payload before any order/invoice is created. Actual branch/profile/car come from the authorized intake result. Only an active owner/authorized branch manager prepares and chooses actual active assigned branch workers with current configured EGP employment. The command is bound to an explicitly selected active branch cashier (possibly the preparing manager/owner). That cashier cannot change the prepared subject/service/assignment/rates. Prepare/current roles are checked before exact replay. Prepare stores actual rate snapshots; place rejects rate/version or service price changes before issuance and requires a new known-closed preparation rather than substituting a value.
- `place_offline_walk_in(p_request uuid)` consumes only that actor's saved exact command under the same fence; validates current service/branch/price and all bindings before creating a real service order, line, reception record and invoice in one TX. `booking_id=NULL,customer_id=NULL`; gross=due and discount0. No synthetic booking slot. Price changed returns deterministic rejection, never silently substitutes.
- `get_offline_walk_in_command(p_request uuid default null)` recovers own prepared payload or actual result. Null recovery finds an unacknowledged own command, including success, so a lost discovery response cannot allow a duplicate. App stores only request UUID before prepare; no phone/car/customer notes locally. Exact result acknowledgement is needed before clearing a successful recovery record.
- `close_offline_walk_in_command(p_request uuid)` atomically closes a prepared command, or returns canonical committed success. It never erases or downgrades a committed order. Absent status is nondefinitive until an authoritative same-mutex tombstone fences the request. Unknown transport results freeze input; no new UUID until actual resolution.
- `ack_offline_walk_in_command(p_request uuid)` marks only a delivered known final result acknowledged; does not delete history. Null discovery must not exclude unacknowledged success. Unknown/active prepared commands cannot be acknowledged into disappearance.

Each result contains stable internal refs for calls, the existing short invoice display reference for humans, actual due/gross/currency, typed source and explicit capabilities: `auth_customer_subject_supported:false,walk_in_loyalty_accrual:false,points_enabled:false,redemption_enabled:false,linked_history_visible:false`. Do not invent a UUID-based customer-visible order number when the shared short invoice number can identify the work order; internal order number can remain internal. Issued invoice snapshots and previous receipts never get rewritten by a later identity link.

## Reception and work

The first migration creates only immutable order-keyed normal arrival records and `received` work. `list_offline_walk_in_reception(p_branch)` returns same-branch received work to management/cashiers or assigned workers, using the actual shared short invoice/order reference. It exposes no enrollment secret, profile history or commission salary/rates. `cancel_offline_walk_in(p_request,p_order,p_reason)` is owner/branch manager only, preserving the existing management-only cancellation policy; cashier-only employees cannot cancel through an accidental definer bypass.

**All direct start/completion transitions on this new typed source are fenced**, including public table updates and service-role callers. A second independently reviewed shared-occupancy migration must implement booking/walk-in resource accounting under the existing shared resource mutex before real work start, VIP changes or completion is supported. Do not label a received-and-invoiced record as completed service. Existing booking queue and work progression remain unchanged.

Retain unpaid cancellation order+void-invoice transaction, reject recorded sale/refund or unresolved gateway attempt and preserve immutable subject/consent/line facts. Paid cancellation/refund uses existing management route, no automatic refund. Same transaction must serialize against existing shift→invoice payment locks, never acquire shift after invoice/order. The existing payment event operation remains the only actual collection ledger.

## Legacy and future gates

Follow-up legacy finalizer patch preserves old receipt replays first, then excludes every new typed walk-in source before any unmanaged/global offer selection. New offline subject cannot be passed into public customer FK routines. Current booking canonical evaluator rejects booking-less sources and remains unchanged. No new guest reward engine or legacy balance conversion.

Typed earning, explicit walk-in policy versions, owner activation, per-source eligibility/refunds, single allocation occupancy across both channels, transaction-specific customer consent and each trusted-link reader adapter are later stages. This contract does not mark them enabled or historically visible.

## Recovery refinements from peer review

The command records immutable `executed_by` at the actual successful placement. Normal recovery is bound-cashier-only; an active owner also discovers their **own actual executions** when recovering without a UUID. Merely preparing an unrelated cashier command does not make it an owner's own pending execution. The bound cashier or actual currently active owner executor may acknowledge a delivered final result, releasing the bound cashier's unresolved slot. This does not grant ordinary staff permission to acknowledge other actors' work.

The stored original creation receipt stays unchanged. Every succeeded get/place replay overlays current actual order status, invoice status and existing `invoice_payment_quote` payment/collectible truth. It exposes `collectible_amount:0` after payment/void while preserving original gross/invoice face amount and immutable IDs. A collected receipt cannot recover as unpaid, nor a cancelled order as received. Rollback cases cover cash/cancel recovery and owner execution → lost-response/null discovery → acknowledgment.
